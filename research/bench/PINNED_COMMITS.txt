# 고정 저장소 — CI 회귀 테스트 코퍼스
#
# 형식: <owner>/<repo> <sha>          (→ 12_ENGINEERING_DECISIONS.md "고정 저장소")
# 대상: 17_MEASUREMENT_BASIS.md "링크 복구 코퍼스" 의 13개
#
# 고정일 2026-08-17. 각 저장소 기본 브랜치 HEAD 를 git ls-remote 로 받았다.
#
# 주의 1 — 이 SHA 는 17 의 원 수치를 만든 커밋이 아니다. 재측정으로 확인했다.
#   원 측정은 2026-08-16 에 수행됐고 그때의 HEAD 가 기록돼 있지 않다.
#   2026-08-17 에 아래 SHA 로 체크아웃해 실험2·실험3 을 다시 돌렸다.
#
#     파일 자동 복구율   95.7%  (원 수치와 동일)   게이트 93%, 여유 2.7%p 유지
#     심볼 자동 복구율   80.0%  (원 수치와 동일)   게이트 78%, 여유 2.0%p 유지
#     심볼 +1클릭       93.6%  (원 93.7% 에서 0.1%p 하락, 제품 목표라 게이트 아님)
#
#   게이트는 조정하지 않았다. 원문 raw_output/rebaseline_2026-08-17.txt
#   재측정 대상은 실험2·실험3 의 코퍼스인 python 4개(django·scikit-learn·
#   flask·requests)다 — 아래 "주의 3" 참조.
#
# 주의 2 — 얕은 클론으로는 이 코퍼스를 쓸 수 없다.
#   링크 복구 측정은 rename 체인을 따라가므로 전체 히스토리가 필요하다
#   (→ research/bench/README.md "resolve/", "symbol/").
#   체크아웃은 아래처럼 한다.
#
#     git clone https://github.com/<owner>/<repo>.git
#     git -C <repo> checkout <sha>
#
#   제안 생성량 측정(M2/M2d)의 R1~R3 는 워킹 트리만 보므로 얕은 클론으로도
#   되지만, R4(git 동시 변경)는 히스토리를 쓴다. 코퍼스를 한 번만 받아
#   전부에 쓰는 편이 단순하다.
#
# 주의 3 — v0.1 CI 는 이 13개가 아니라 그중 python 4개에서만 돌린다. (2026-08-17 확정)
#   실험2(파일 95.7%)·실험3(심볼 80.0%)은 django·scikit-learn·flask·requests
#   에서만 측정됐다. 나머지 9개(go 3 / typescript 3 / rust 3)는 M1
#   (언어별 심볼 복구율)에서만 쓰였고, 그 결과는 언어별로 80.2~94.5% 로 퍼진다.
#
#   즉 CI 게이트를 13개 전체에서 돌리면 78% / 93% 가 그대로 성립하는지 모른다.
#   → v0.1 은 python 4개에서만 돌린다. Go/TS/Rust 파서는 Phase 2 에서야 생기므로
#     그 전에는 게이트를 걸 대상 코드가 없다. Phase 2 에서 나머지 9개로 확장하고
#     게이트 값을 다시 유도한다. (→ 12 "게이트의 모집단")
#
# 주의 4 — 게이트는 합산과 저장소별 두 가지다.
#   저장소별 자동 복구율이 66.1~82.4% 로 퍼진다. 합산 80.0% 는 심볼 수가 많은
#   django(16,935/20,837)에 끌려간 값이다. 합산만 걸면 큰 저장소가 작은 저장소의
#   회귀를 가린다.
#
#     합산      자동 심볼 > 78%   (실측 80.0%,       여유 2.0%p)
#     저장소별  자동 심볼 > 63%   (실측 최저 66.1%,  여유 3.1%p)
#     합산      자동 파일 > 93%   (실측 95.7%,       여유 2.7%p)
#     저장소별  자동 파일 > 47%   (실측 최저 50.6%,  여유 3.6%p, requests)
