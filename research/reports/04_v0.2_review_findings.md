# v0.2 문서 검토 결과

검토 방식: 독립 검토자(문서만 받고 구현해야 하는 입장) + 작성자 자체 대조. 모든 지적은 문서에서 해당 문장을 직접 확인했다. 추정으로 만든 항목은 없다.

**결과: blocker 6, major 7, minor 3.**

가장 중요한 구조적 발견은 이것이다.

> **blocker 6건이 전부 같은 원인이다 — `.vault/` 에 영구 기록되는 데이터의 형식이 정의되지 않았다.**

v0.2는 "무엇을 저장할지"는 정했지만 "어떤 형식으로 저장할지"는 정하지 않았다. 그리고 `.vault/` 는 git 커밋 대상이며 사용자가 실제로 건 링크가 들어가는 곳이다. 나중에 바꾸면 사용자 데이터를 마이그레이션해야 한다.

# BLOCKER

## B1. S4를 구현할 수 없다 — 과거 심볼의 스케치를 저장할 곳이 없다

`04_VAULT_AND_DATA_MODEL.md`:
> S4  본문 유사도 Jaccard ≥ 0.40 → 후보 제시
> 파서가 이미 심볼 본문 범위(`range`)를 알고 있으므로 추가 파싱 없이 **인덱싱 시점에** 계산한다.

S4는 "사라진 옛 심볼의 본문"과 "현재 vault의 심볼"을 비교해야 성립한다. 그런데 스케치는 `.vault-ai/similarity/` 에 있고 이는 **현재 파일에서 재생성되는 파생물**이다. 옛 심볼은 파일에서 이미 사라졌으므로 그 스케치는 재생성이 불가능하다.

`.vault/` 의 파일 목록은 `links.jsonl` / `aliases.jsonl` / `decisions.jsonl` 셋뿐이고, `links.jsonl` 스키마에 스케치 필드가 없다.

**왜 놓쳤나**: 벤치마크에서는 git에서 과거 커밋의 본문을 꺼낼 수 있었다. 제품에서는 사용자가 링크를 건 시점의 본문이 커밋되어 있다는 보장이 없고, git이 없는 vault도 허용한다(`04`: "Vault는 사용자의 일반 로컬 폴더다").

S4는 4.5%p를 담당하며 93.7% 목표의 구성요소다. 빼고 갈 수 없다.

**대응 방향**: 링크 생성 시점의 스케치를 `links.jsonl` 레코드에 함께 기록. 32개 해시 = 레코드당 약 200바이트. 다만 "`.vault/` 는 사람이 읽을 수 있음"과 충돌하므로 별도 사이드카 파일(`sketches.jsonl`)로 분리하는 편이 낫다.

## B2. `vault://` 주소 문법이 정의되어 있지 않다

`04` 는 예시만 나열한다. 다음이 전부 미정이다.

- **heading slug 규칙** — `#teacher-router` 가 어떤 heading에서 나오는지. 대소문자, 공백, 문장부호, **한글/유니코드**, 같은 이름의 heading이 두 개일 때. 문서 전체에서 `slug` / `슬러그` / `중복 heading` 이라는 단어가 **0회** 등장한다.
- **fragment 네임스페이스 충돌** — `#/`(JSON pointer), `#col:` `#row:` `#cell:`(접두사), `#Sym.Sub`(qualname), `#slug`(heading)이 한 네임스페이스에 섞여 있다. `.md` 에 `col:label` 이라는 heading이 있으면?
- **이스케이핑** — 파일명에 `#`, 심볼명에 `.`(Rust `impl`, TS 네임스페이스).

`12_ENGINEERING_DECISIONS.md` 의 미결 목록에도 없다. 즉 **결정된 것으로 취급되고 있으나 실제로는 결정되지 않았다.**

## B3. `links.jsonl` 레코드에 ID가 없어 tombstone·재지정을 구현할 수 없다

스키마:
```json
{"from":"...","rel":"describes","to":"...","origin":"manual","ts":"..."}
```

식별자가 없다. `(from, rel, to)` 튜플에 의존해야 하는데:

- `09_DESKTOP_UX.md` 의 **"47건을 일괄 수정할까요?"** 는 `to` 를 바꾸는 동작이다. append-only에서는 "tombstone + 새 레코드"인데, 원래 `ts` 와 재지정 이력이 어디 남는지 미정.
- 같은 `(from, rel, to)` 를 두 번 걸고 한 번만 지우는 경우가 표현 불가.
- `09` 는 BROKEN 링크에 **"마지막으로 알려진 주소를 함께 보여준다"** 고 하는데 그 필드가 스키마에 없다.

같은 문제가 S3/S4의 "1클릭 확정" 결과에도 있다. 확정 결과를 `links.jsonl` 에 새 레코드로 쓰는지, `aliases.jsonl` 에 심볼 alias로 넣는지 정의가 없다. `04` 는 alias 소스를 watcher와 git 둘로 못박았으므로 **사용자 확정은 소스 목록에 없다.**

## B4. `rel` 어휘가 정의되지 않았고, 예시가 미정의 rel을 쓴다

정의된 rel: `defined_in` `contains` `parent_of` `imports` `json_pointer` `calls` `inherits` `changed_in` `introduced_in` `renamed_from` `co_changed` `describes` `references` `mentions` `uses`.

그런데:

| 미정의 rel | 등장 문서 |
|---|---|
| `configured_by` | 01, 08 |
| `tested_by` | 01, 07, 08 |
| `described_by` | 08 |
| `implemented_by` | 01 |

`08_MCP_AND_AI.md` 는 `vault.backlinks` 를 `neighbors(direction="in")` 으로 흡수한다고 써놓고, 정작 응답 예시에서 역관계 이름(`described_by`)을 쓴다. **역관계를 저장하는지 방향으로만 표현하는지가 모순이다.**

`12` 는 rel 표준화를 **Phase 4** 로 미뤘다. 그러나 rel은 **Phase 3에서 이미 `.vault/links.jsonl` 에 영구 기록된다.** 되돌리기 비싼 것이 늦은 Phase에 있다.

## B5. "심볼 링크 복구율 > 93%" CI 회귀 테스트는 사람의 클릭 없이 도달 불가능하다

`05` / `10` / `12` / `14` 네 문서가 전부 93%를 요구한다. 그런데 실측 분해는:

```text
자동 복구 계(S1+S2)   80.0%
S3 qualname 유일       9.1%   → 후보 제시 (1클릭 확정)
S4 본문 유사도         4.5%   → 후보 제시 (1클릭 확정)
+1클릭 계             93.7%
```

**93.7%는 사용자가 클릭했을 때의 수치다. CI는 클릭하지 않는다.** 자동 도달 상한은 80.0%이므로 이 테스트는 구현이 완벽해도 항상 실패한다.

파일 쪽도 문제다. CI 목표 `> 95%` vs 실측 `95.7%` — **여유가 0.7%p뿐이다.** 게다가 `12` 는 "고정 저장소 히스토리"라고만 쓰고 어느 저장소인지 지정하지 않았다. 95.7%는 Python 저장소 4개에서 나온 값이므로 다른 저장소를 고르면 임계값이 무의미해진다.

## B6. 파일·심볼 이외 주소의 해석 계단이 전혀 없다

`04` 가 정의한 계단은 "파일 주소 — 3단"과 "심볼 주소 — 5단" 둘뿐이다. 그런데 같은 문서가 `DocumentSection` `JSONProperty` `YamlNode` `Column` `Row` `NotebookCell` 을 주소 지정 가능 객체로 나열한다.

미정의 구간에서 실제로 막히는 것:

- CSV 앞에 행 하나가 삽입되면 `#row:1042` 는 다른 행을 가리킨다. L1이 "HIT"인가 오해석인가?
- 노트북 셀 순서가 바뀌면 `#cell:12` 는?
- **heading을 수정하면 `#teacher-router` 는 즉시 BROKEN이 된다.**

마지막이 특히 심각하다. R1이 만드는 문서↔코드 링크의 **문서 쪽 끝점이 전부 이 주소**이고, `01_PRODUCT_VISION.md` 가 "이 하나만 잘 돌아가도 제품이 성립한다"고 선언한 기능이다. heading 리네임은 파일 리네임보다 훨씬 흔한데 alias 소스가 없다.

실측 95.7% / 93.7%는 파일과 심볼만 측정한 값이므로 **이 구간의 복구율은 미지수다.**

# MAJOR

## M1. 커밋 전 rename에는 alias 소스가 없다 + 두 문서가 watcher 신뢰도를 반대로 말한다

```text
03  "rename은 특히 신뢰할 수 없어서 delete + create로 도착하는 경우가 잦다."
04  "Watcher rename 이벤트 — 신뢰도는 높지만 항상 도착하지 않는다"
```

표현 차이가 아니라 구현 분기다. watcher rename을 alias로 바로 쓸지 검증 후 쓸지가 갈린다.

더 큰 공백: 정합성 스캔의 비교 키는 `(path, mtime_ns, size)` 이므로 rename을 delete+create로만 볼 수 있고 alias를 **만들 수 없다.** git rename detection은 커밋 이후에만 작동한다. 따라서 **이름을 바꾸고 아직 커밋하지 않은 구간에서 L2/S2가 통째로 빈다.** 실사용에서 가장 흔한 시나리오(방금 이름 바꿈 → 링크 확인)인데, 측정은 전부 커밋된 히스토리 기반이라 이 갭을 재지 않았다.

또한 **git이 없는 vault에서 복구율이 88.2% / 70.4%로 떨어진다는 사실이 어느 문서에도 표기되지 않았다.**

## M2. AI 제안을 `.vault-ai/` 에 저장 — v0.1이 지적한 모순의 재발

`08`: "서버가 불변 suggestion_id 발급, **`.vault-ai/suggestions/` 에 저장**"
`02` 원칙 3: "`.vault-ai/` 순수 파생물. **언제든 삭제 가능**"

결정론적 제안(R1~R5)은 재스캔으로 재생성되므로 맞다. 그러나 **AI가 MCP로 밀어넣은 미승인 제안은 재생성되지 않는다.** `03` 이 v0.1의 결함으로 지목한 것과 정확히 같은 구조다.

부수 효과: `10` 의 Phase 0 종료 조건 "`.vault-ai/` 삭제 후 재인덱싱으로 **완전 복구**"가 Phase 4 이후 판정 불가가 된다.

추가로 `16` 은 "거절한 것은 `decisions.jsonl` 에 기록되어 다시 나오지 않는다"고 하는데, suggestions를 지우고 재생성하면 `suggestion_id` 가 달라진다. **decisions와 재생성 후보를 매칭하는 키가 정의되어 있지 않다.**

## M3. `/` 자동 확장이 성능 예산을 스스로 깬다

`09`: "`src/router`  [경로]  ← **'/' 입력 시 자동 확장**"
`05`: 경로 전체 100K = **18.8ms (예산 초과)**, "경로 전체 스코프는 **50K까지** 보장"

100K vault에서 사용자가 `src/` 를 치는 순간 시스템이 **자동으로** 예산 초과 경로에 진입한다. 사용자 선택이 아니라 자동 전환이므로 "50K까지 보장"이라는 단서가 실효가 없다. 대응책(결과 수 제한, 예산 완화, 경고)이 문서에 없고 `12` 의 미결 항목에도 없다.

## M4. "저장 → 인덱스 반영 < 200ms" 목표와 "debounce 100~300ms"가 직접 충돌

`05` 성능 목표: `파일 저장 → 인덱스 반영 | < 200 ms | —`
`05` 성능 원칙 / `03`: `파일 변경 debounce 100~300ms`

debounce 상한 300ms를 쓰면 파싱·인덱싱을 0ms에 끝내도 목표를 넘는다. 게다가 이 항목만 **조건란이 비어 있고**, `17_MEASUREMENT_BASIS.md` 확정 수치 표에도 없다 — **실측 근거 없는 유일한 성능 목표다.**

## M5. R2가 `.toml` 파싱을 요구하는데 초기 지원 형식에 없다

`16` R2: "**JSON / YAML / TOML** 값이 vault 안의 실존 파일 경로면" + 예시 `pyproject.toml`
`06` / `14` 초기 형식: `.json .yaml .csv` — **`.toml` 없음**
`13`: `.toml` 을 **향후 형식**으로 분류
`10` Phase 2 목록에도 없음

그런데 `.vault/vault.toml` 자체가 TOML이다. 그리고 `16` 이 "TypeScript는 12건에 그쳤다. 이런 경우 **R2와 R4가 주력**"이라고 한 저장소들이 대개 `Cargo.toml` / `pyproject.toml` 기반이다.

## M6. Phase 종료 조건 4건이 측정 불가 또는 무의미

| Phase | 종료 조건 | 문제 |
|---|---|---|
| 0 | 10K 파일 정합성 스캔 < 1s | `14` 의 실제 목표는 500ms @ **100K**, 실측 281ms. **약 35배 느슨해서** 통과해도 아무것도 검증 안 됨 |
| 1 | keystroke p95 < 16ms @ 100K | `14` 는 "**4코어+**" 조건이 붙는데 `10` 과 `12`의 CI 블록에는 없다. CI 러너 스펙 미지정 → 러너가 바뀌면 임의로 실패. `02` 원칙 8을 문서가 스스로 어김 |
| 3 | 제안 후보 100건 이상 | "실제 프로젝트" 미지정. `16` 측정표에서 **TypeScript는 12건**. 저장소 선택으로 통과/실패가 결정됨 |
| 4 | AI가 3회 호출 이내 해결 | `08` 은 "질의 20개 평균"으로 쓰는데 `10` 은 평균인지 전건인지, 어느 모델인지 미지정. `08` 자신이 "모델 하네스 없이는 잴 수 없다"고 적음 |

## M7. 제품의 핵심 주장에 검증 게이트가 없다

```text
01  R1(문서 백틱 ↔ 심볼)에 대해 "이 하나만 잘 돌아가도 제품이 성립한다"
16  "정밀도 수치를 이 문서에 명시하지 않는다" (측정 불가 인정)
10  Phase 3 종료 조건 = 링크 생성 3클릭 / 제안 후보 100건 / 심볼 복구율 93%
```

Phase 3 종료 조건은 제안의 **양**만 잰다. 제품이 성립하는 근거라고 선언한 **질**(정밀도·승인율)에 대한 게이트가 전 Phase 어디에도 없다. `10` 이 산문으로 "미측정 검증 항목: 제안 승인율"을 적어두었으나 종료 조건 블록에는 없으므로 **게이트가 아니라 메모다.**

blocker 6건 중 5건(B1~B4, B6)과 minor 2건이 여기로 수렴한다. 담아야 할 것:

```text

  경로 부분 정규화 (Windows, 유니코드, 대소문자)
  fragment 타입 접두사 체계 — 네임스페이스 충돌 제거
```

## 4. 이번 검토가 시사하는 것

v0.2는 **"무엇을 만들지"와 "왜 그렇게 만들지"는 측정으로 단단해졌지만, "정확히 어떤 바이트를 디스크에 쓸지"는 v0.1과 같은 수준으로 남아 있다.**

측정이 답한 것은 설계 판단(파서 백엔드, 검색 스코프, 계단 구조)이었고, 스키마는 측정 대상이 아니었기 때문에 자연스럽게 비었다. 그런데 **되돌리기 비용은 스키마 쪽이 더 크다** — 파서는 바꿔도 재파싱하면 되지만, 사용자가 이미 건 링크의 형식은 마이그레이션해야 한다.

`18_DATA_FORMATS.md` 를 쓰기 전에는 Phase 0을 시작하지 않는 것을 권한다.
