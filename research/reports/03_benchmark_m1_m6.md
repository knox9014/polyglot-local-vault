# M1 — 언어별 심볼 복구율

2차 보고서의 가장 큰 한계는 "Python 생태계만 측정"이었다. Go / TypeScript / Rust 저장소 9개를 전체 히스토리로 클론해 동일한 계단(S1~S4)을 적용했다.

## 50% 커밋 경과 기준

| 언어 | 저장소 | 심볼 | live | S1 | S2 | S3u | S4 | **자동** | **+1클릭** |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| typescript | 2 | 2,314 | 2,185 | 83.6% | 10.9% | 2.6% | 0.4% | **94.5%** | **97.5%** |
| rust | 3 | 9,584 | 8,162 | 70.9% | 17.5% | 2.5% | 2.9% | **88.4%** | **93.7%** |
| go | 3 | 4,945 | 3,502 | 81.3% | 4.3% | 5.6% | 0.4% | **85.6%** | **91.6%** |
| python | 2 | 25,006 | 19,668 | 71.9% | 8.3% | 9.2% | 4.3% | **80.2%** | **93.7%** |

## 결론

### ① 2차 결과는 낙관이 아니라 **보수적**이었다

Python이 자동 복구율 **최하위(80.2%)** 였다. 다른 언어는 85.6~94.5%다. 2차 보고서에서 "Python 편중이 한계"라고 적었는데, 편향의 방향이 유리한 쪽이 아니라 불리한 쪽이었다. 설계 판단은 그대로 유지된다.

### ② +1클릭 최종 복구율은 언어를 가리지 않고 안정적이다 (91.6~97.5%)

경로는 다르다. Python은 S3u+S4가 13.5%p를 채우고, TypeScript는 3.0%p만 채운다. 하지만 최종 숫자는 수렴한다. **계단식 해석 설계가 언어 독립적으로 작동한다는 증거다.**

### ③ 대규모 구조 개편에서 git alias가 전부를 구한다

측정 중 **S1 = 0** 인 케이스가 5건 나왔다.

| 저장소 | 시점 | S1 | S2 | 자동 복구 |
|---|---|---:|---:|---:|
| prettier | 2019-02 | 0 | 546 | 97.7% |
| date-fns | 2023-01 | 0 | 689 | 95.7% |
| clap | 2018-01 | 0 | 398 | 75.5% |
| serde | 2016-07 | 0 | 314 | 64.9% |
| tokio | 2018-04 | 0 | 5 | 8.6% |

전체 파일이 이동한 순간인데도 git alias만으로 64~98%가 복구됐다. **1차 보고서의 "Git을 Phase 6 → Phase 0" 권고가 다시, 더 강하게 확인됐다.**

(tokio 2018은 저장소 자체가 사실상 다른 프로젝트였던 시기라 예외.)

## 정밀도 — 자동 필터 두 개가 실패했다

개수는 충분했지만 정밀도가 문제였다. 자동 판정 지표를 두 번 시도했고 **둘 다 실패했다.**

### 실패 ① 지역성 필터 (M2b)

"문서와 대상 심볼이 같은 최상위 서브트리에 있으면 정답일 개연성이 높다"고 가정했다.

| repo | 지역성 |
|---|---:|
| django | 0.0% |
| hugo | 0.0% |
| cpython | 0.3% |
| kubernetes | 13.1% |

거의 0이다. 이유는 샘플을 보면 즉시 드러난다.

```
django   docs/faq/admin.txt        `ModelAdmin`         → django/contrib/admin/options.py   ← 정답
hugo     docs/.../postcss.md       `PostCSS`            → tpl/css/css.go                    ← 정답
cpython  Misc/NEWS.d/3.9.0b1.rst   `get_source_segment` → Lib/ast.py                        ← 정답
```

**표준 레이아웃은 `docs/` 와 `src/` 를 분리한다.** 즉 이 제품이 노리는 문서↔코드 관계는 본질적으로 트리를 가로지른다. 지역성으로 거르면 **가장 가치 있는 제안을 정확히 버린다.**

### 실패 ② 산문 빈도 필터 (M2c)

"그 토큰이 문서 산문(백틱 밖)에 자주 나오면 영단어다"라고 가정했다. 외부 사전 없이 vault 자체로 계산되는 우아한 규칙이었는데, 제거 목록을 보면 참담하다.

```
✗ `LoadBalancerSourceRanges` (산문 8회)   ← 1차에서 최고의 예시였던 그것
✗ `ModelAdmin`               (산문 250회)
✗ `lru_cache`                (산문 37회)
✗ `fetch_20newsgroups`       (산문 8회)
✗ `RandomizedSearchCV`       (산문 4회)
✗ `PostCSS`                  (산문 28회)
```

**좋은 문서는 API 이름을 산문에서도 반복한다.** 산문 빈도는 "영단어임"이 아니라 "그 문서의 주제임"의 신호였다. 정확히 거꾸로 읽었다. 제안의 50.7%가 날아갔고 그중 상당수가 정답이었다.

### 작동한 것 ③ 영어 사전 필터 (M2d)

진짜 오탐의 공통점은 빈도도 위치도 아니라 **그 토큰이 영어 단어라는 것**이었다.

## M2 결론

1. **콜드스타트는 해결된다.** 가장 엄격한 필터를 거쳐도 저장소당 평균 **1,970건**, 최소 12건(TypeScript, 문서가 적은 저장소), 대부분 수백~수천 건이다. Day 1 화면에 "관계 후보 N건"을 띄울 수 있다.
2. **자동 필터로 완벽을 노리면 안 된다.** 세 가지 필터 중 둘이 실패했고, 성공한 것도 실존 심볼을 버린다. 설계 결론은 **필터로 걸러내지 말고 랭킹해서 보여주고 사용자가 1클릭으로 확정**하게 하는 것이다. 리뷰 §3의 "1클릭 승인" 구조가 맞았다.
3. **vendor/third-party 제외는 성능이 아니라 정밀도 문제다.** node는 vendor 포함 시 764건 → 제외 시 155건이었고, 제외된 609건은 대부분 `deps/v8/third_party` 같은 무관한 코드였다. ignore 규칙을 리뷰 §12의 "구현 중 결정" 항목에서 **Phase 0 필수 항목**으로 올려야 한다.
4. **문서 형식은 `.md`만으로 부족하다.** django(`.txt`), cpython/scikit-learn(`.rst`)은 `.md`를 거의 안 쓴다. `.md`만 지원하면 이 저장소들에서 R1이 0이 된다. 문서 06의 v0.1 지원 목록에 `.rst`/`.txt`를 넣어야 한다.

# M3 — call edge 정확도 (리뷰 §4)

리뷰 §4의 주장:

> 타입 추론 없이 이름 매칭으로 call edge를 만들면 **오탐이 정탐보다 많아진다.**
> v0.1 파서 범위에서 `calls`를 빼는 것을 권한다.

실제 저장소 5개의 **호출부 360,893개**를 추출해 이름 해석 가능성을 셌다.

| repo | lang | 호출부 | UNIQUE | AMBIG | EXTERN | 유일률 |
|---|---|---:|---:|---:|---:|---:|
| django | python | 187,887 | 59,045 | 71,126 | 57,716 | 45.4% |
| scikit-learn | python | 109,537 | 35,068 | 26,597 | 47,872 | 56.9% |
| hugo | go | 50,388 | 14,268 | 18,229 | 17,891 | 43.9% |
| gin | go | 9,175 | 2,704 | 2,107 | 4,364 | 56.2% |
| flask | python | 3,906 | 1,262 | 1,112 | 1,532 | 53.2% |

```
전체 호출부                      : 360,893
UNIQUE (vault 내 정의 정확히 1개) : 112,347 (31.1%)
AMBIG  (2개 이상)                : 119,171 (33.0%)
EXTERN (0개 — 외부/빌트인)       : 129,375 (35.8%)

>>> vault 내부로 해석되는 호출 중 유일 매칭 = 48.5%
>>> 모호(오탐 위험) 비율                    = 51.5%
```

**주장이 문자 그대로 확인됐다. 51.5% > 48.5%.**

## 그런데 호출 형태별로 나누면 그림이 완전히 달라진다

| 형태 | 건수 | UNIQUE | AMBIG | EXTERN | 유일률 |
|---|---:|---:|---:|---:|---:|
| `foo()` bare | 121,647 | 56,613 | 20,895 | 44,139 | **73.0%** |
| `self.foo()` | 53,238 | 15,167 | 4,969 | 33,102 | **75.3%** |
| `obj.foo()` attr | 186,008 | 40,567 | 93,307 | 52,134 | **30.3%** |

**모호도는 `obj.method()` 한 형태에 몰려 있다.** 그리고 그게 전체 호출부의 51.5%(186,008/360,893)다.

- `foo()` — 모듈 스코프. 임포트 정보와 결합하면 더 올라간다. 73.0%
- `self.foo()` — 리시버가 확정적이라 클래스 스코프로 좁힐 수 있다. 75.3%
- `obj.foo()` — 리시버 타입을 모르면 해석 불가. **30.3%**

## M3 결론 — 리뷰 §4의 권고를 수정한다

리뷰에서는 "`calls`를 통째로 빼라"고 했다. **너무 거칠었다.** 데이터가 말하는 것은 형태별 분리다.

```
v0.1에서 생성할 것
  bare  foo()        → confidence = probable  (73.0%)
  self  self.foo()   → confidence = probable  (75.3%)
     ※ 둘 다 전체 호출부의 48.5% (174,885건). 버리기엔 너무 많다.

v0.1에서 생성하지 말 것
  attr  obj.foo()    → 유일률 30.3%. 오탐이 정탐의 2.3배.
     ※ 타입 추론(Pyright/gopls 등) 도입 후 v0.2에서.
```

리뷰 §4에서 제안한 `confidence` 필드(`certain` / `probable` / `heuristic`)는 유지하되, **`attr` 호출은 아예 edge를 만들지 않는다**가 정확한 결론이다.

# M4 — Watcher Reconciliation 비용 (리뷰 §5)

리뷰 §5의 추정:

> `(path, mtime_ns, size)` 튜플만 비교하는 스캔은 10만 파일에서 1초 미만이다.

실제 디스크의 **229,062 파일 / 17,733 디렉터리 / 2.7GB** 로 측정했다.

| 모드 | 시간 | 파일/ms |
|---|---:|---:|
| 1회차 (cold-ish) | 753 ms | 304 |
| 2~4회차 최소 (warm) | **644 ms** | 356 |
| ignore 미적용 | 616 ms | 377 |
| 병렬 2 워커 | 1,470 ms | 156 |
| 병렬 4 워커 | 2,137 ms | 107 |

| 항목 | 값 |
|---|---:|
| diff (변경 없음) | 129 ms |
| diff (1% 변경 주입) | 123 ms, 2,290건 탐지 |
| 인덱스 상태 메모리 | 31.5 MB / 229K 파일 |

**규모별 외삽:**

| 파일 수 | warm 스캔 |
|---:|---:|
| 1,000 | 3 ms |
| 10,000 | 28 ms |
| 50,000 | 140 ms |
| **100,000** | **281 ms** |
| 232,000 | 652 ms |

## 결론

**§5의 추정이 확인됐다.** 10만 파일 281ms + diff 60ms ≈ **0.35초**. 유휴 시 주기 실행에 전혀 부담이 없다.

주의할 점 하나: **병렬화가 오히려 느렸다.** 이건 Python GIL + `scandir`의 락 경합 때문이며 Rust 구현에는 적용되지 않는다. 다만 **디스크 메타데이터 스캔은 I/O 바운드라 병렬화 이득이 작다**는 방향성은 유효하다. 굳이 병렬화하지 말고 단일 스레드로 두는 게 낫다.

# M5 — 유사도 파라미터 스윕 (2차의 미해결 항목)

2차 보고서에서 "4-gram / 스케치 96 / 임계 0.60은 첫 시도값이라 튜닝 여지가 있다"고 적었다. django 50% 경과 지점에서 45개 조합을 스윕했다.

**정밀도 측정 방법**: S3u(qualname 전역 유일)로 해결된 심볼은 정답을 안다. 그 집합에 S4 매처를 돌려 같은 대상을 고르는지 보면 사람 검수 없이 정밀도를 정량화할 수 있다.

## 주요 결과 (S4 대상 5,155건 / 정답지 1,119건)

| k | sketch | thr | 인덱스 항목 | S4 복구 | 정밀도 |
|---:|---:|---:|---:|---:|---:|
| **3** | **32** | **0.40** | **946,094** | **1,515** | **92.9%** |
| 3 | 32 | 0.50 | 946,094 | 1,253 | 93.6% |
| 3 | 96 | 0.60 | 1,525,270 | 954 | 93.4% |
| 4 | 96 | 0.60 | 1,518,274 | 809 | 92.3% |  ← 2차에서 쓴 값
| 5 | 256 | 0.80 | 1,924,160 | 494 | 91.9% |

## 결론

### ① 정밀도는 파라미터에 거의 무관하다 (91.6~93.6%)

45개 조합 전부가 92% 언저리다. 즉 **임계값을 낮춰도 오답이 늘지 않는다.** 이건 유사도 분포가 이봉형(같은 함수는 매우 유사, 다른 함수는 매우 다름)이라는 뜻이다.

### ② 임계값만 낮추면 복구가 87% 늘어난다

```
2차 설정 (k=4, sketch=96, thr=0.60) : 809건 복구, 정밀도 92.3%
최적     (k=3, sketch=32, thr=0.40) : 1,515건 복구, 정밀도 92.9%
                                      → +87% 복구, 정밀도 오히려 +0.6%p
```

django 기준으로 S4 기여가 **4.8%p → 8.9%p** 로 거의 두 배가 된다.

### ③ 스케치 크기 96 → 32 로 줄여도 결과가 동일하다

인덱스 항목 152만 → 95만 (**-38%**). 결과는 소수점까지 같다. 메모리를 그냥 버리고 있었다.

**권장 설정: `shingle k=3, sketch=32, threshold=0.40`**

# M6 — 전문검색 인덱스 규모 (리뷰 §11)

리뷰 §11에서 근거 없이 "인덱스 크기 / 원본 < 25%"를 목표로 썼다. 실제로 역인덱스를 구축해 검증했다.

| 항목 | 값 |
|---|---:|
| 인덱싱된 파일 | 226,868 |
| 제외 (바이너리 2,097 / 1MB 초과 97) | 2,194 |
| 원본 텍스트 | 1,329.3 MB |
| 총 토큰 출현 | 135,217,444 |
| 고유 term | 2,034,963 |
| posting (term-doc 쌍) | 25,308,080 |
| posting 리스트 (delta+varint) | 31.3 MB |
| term dictionary | 41.5 MB |
| **인덱스 합계** | **72.8 MB** |

```
>>> 인덱스 / 원본 = 5.5%   (목표 < 25%)
>>> 구축 시간     = 41.9 s  (5,420 파일/s, 31.8 MB/s, 단일 스레드)
```

**규모별 외삽:**

| 파일 수 | 인덱스 크기 | cold 구축 |
|---:|---:|---:|
| 1,000 | 0.3 MB | 0.2 s |
| 10,000 | 3.2 MB | 1.8 s |
| 50,000 | 16.0 MB | 9.2 s |
| **100,000** | **32.1 MB** | **18.5 s** |
| 226,868 | 72.8 MB | 41.9 s |

**고빈도 term 컷 효과:**

| 상위 N개 제거 | posting 절감 |
|---:|---:|
| 10 | 3.5% |
| 100 | 17.3% |
| 1,000 | 45.1% |
| 10,000 | 67.3% |

## 결론 — 그리고 이 수치의 한계

**5.5%는 목표(25%)의 5분의 1이다.** 다만 이 인덱스는 **doc ID만** 저장한다. 실제 제품에는 더 필요하다.

| 추가 항목 | 증가 추정 | 누적 비율 |
|---|---|---:|
| 기본 (doc ID만) | — | 5.5% |
| + term frequency (BM25용, ~1B/posting) | +24 MB | 7.3% |
| + 위치 정보 (구문 검색용, ~1.5B/토큰 출현) | +193 MB | **21.8%** |

**위치 정보까지 넣으면 21.8%로 목표에 근접한다.** 즉 §11의 25%는 우연히도 적절한 값이었지만, "위치 정보를 넣을 것인가"가 그 목표의 성립을 좌우한다.

→ **설계 결정 필요**: 구문(phrase) 검색을 v0.1에 넣을 것인가? 안 넣으면 7.3%로 여유롭고, 넣으면 21.8%로 빠듯하다. 문서 05의 검색 문법 예시에 구문 검색이 없으므로 **v0.1에서는 제외하고 7.3%를 목표로 하는 것**을 권한다.

또 하나: cold indexing 100K 파일 **18.5초**는 리뷰 §11에서 제시한 목표(`< 3분`)의 6분의 1이다. **목표가 지나치게 느슨했다.** 30초로 조여야 의미 있는 기준이 된다.

# 측정 한계 (전체)

1. **2코어 Xeon 2.1GHz.** 실사용 머신(8~16코어)보다 훨씬 약하다. 병렬 효율 0.86을 함께 측정해 외삽 근거를 남겼다.
2. **제안 엔진 정밀도에 사람 검수가 없다.** 자동 지표 두 개가 실패했고, 세 번째(사전 필터)도 `Ridge`/`Lasso` 같은 실존 심볼을 버린다. 최종 정밀도 수치는 제시하지 않았다 — **측정하지 못한 것을 측정한 척하지 않기 위해서다.**
3. **M3의 UNIQUE 판정은 이름 단위다.** 임포트 정보를 결합하면 `bare` 유일률은 73.0%보다 올라간다. 즉 이 값은 **하한**이다.
4. **M6의 인덱스는 doc ID만 저장한다.** TF/위치 포함 시 추정치를 별도로 제시했으나 실측은 아니다.
5. **M1의 TypeScript 표본이 작다** (2 저장소, 2,314 심볼). date-fns는 과거에 `.js`였고 prettier는 `.mjs` 비중이 커서 `.ts` 심볼이 적었다. 다른 언어보다 신뢰도가 낮다.
6. **모든 언어에서 vendored 코드를 제외했다.** 실제 사용자 vault도 그럴 것이므로 타당하지만, `.gitignore` 기반 자동 제외가 전제된다.
