# Polyglot Local Vault — 설계 가정 실측 보고서

리뷰 문서 §15에서 제안한 두 실험을 **실제 데이터로** 수행한 결과다.
합성 데이터는 쓰지 않았다. 내가 만든 경로/히스토리로 측정하면 내 가정을 내가 확인하는 것에 불과하기 때문이다.

## 실험 환경

| | |
|---|---|
| CPU | Intel Xeon @ 2.10GHz, **2 코어** |
| 구현 | Rust 1.x, `opt-level=3`, `lto=true`, `codegen-units=1` |
| 의존성 | `memchr` 2.8 (SIMD 바이트 검색) 외 없음 |
| 측정 | 워밍업 3회 후 15~20회 반복, p50/p95/p99 |

> **주의:** 2코어는 실사용 개발 머신(8~16코어)보다 훨씬 약하다. 절대값이 아니라 **한계점의 위치와 각 최적화의 상대 기여도**를 보는 것이 이 실험의 목적이다. 코어 스케일링을 별도로 측정해 외삽 근거를 남겼다.

# 실험 1 — 검색 속도

## 검증 대상 가정

리뷰 §6에서 내가 이렇게 주장했다.

> 10만 파일의 경로 문자열 전체는 메모리로 대략 10MB다. 통째로 올려놓고 선형 스캔하면 퍼지 매칭 포함 **수 ms**에 끝난다.

**이 주장은 틀렸다.** 아래가 실측이다.

## 코퍼스

실제 저장소 5개를 클론해 경로를 추출했다.

| 저장소 | 파일 수 |
|---|---:|
| microsoft/TypeScript | 81,368 |
| rust-lang/rust | 62,013 |
| nodejs/node | 51,368 |
| kubernetes/kubernetes | 31,300 |
| python/cpython | 6,077 |
| **합계** | **232,126** |

- 경로 평균 길이 **68.0 바이트**, 최대 242
- 원시 텍스트 **15.3 MB** (→ 100K 환산 약 6.6MB. 리뷰의 "10MB" 추정은 대략 맞았다)
- 상주 메모리 **31.9 MB** (원본 + 소문자 정규화본 + 오프셋/인덱스)
- 깊이 분포: depth 4가 최빈(104,410), 최대 15

## 1-1. 최초 구현 결과 — 예산 초과

fzf 계열 퍼지 매칭(부분수열 + DP 스코어링, 경계/camelCase/연속/파일명 보너스), 64비트 문자 비트마스크 프리필터, top-50 bounded 선택.

**232,126 경로, 2스레드, p95:**

| query | p95 |
|---|---:|
| `r` | 22.8 ms |
| `rout` | 38.5 ms |
| `route` | 47.1 ms |
| `testsr` | **55.7 ms** |
| `config` | 21.7 ms |

60fps 1프레임 예산이 **16ms**인데 최악 56ms. 리뷰 §6의 "수 ms" 주장은 이 규모에서 성립하지 않는다.

### 프리필터가 거의 무용지물이었다

64비트 문자 집합 비트마스크의 통과율:

| query | 마스크 통과 | 비율 |
|---|---:|---:|
| `r` | 226,133 / 232,126 | 97.4% |
| `test` | 224,395 | 96.7% |
| `router` | 166,195 | 71.6% |
| `zzq` | — | **20.7x 가속** |

흔한 문자로 된 짧은 쿼리(=사용자가 실제로 타이핑하는 것)에서는 아무것도 걸러내지 못한다. 존재하지 않는 문자 조합(`zzq`)에서만 극적으로 작동하는데, 그건 사용자가 거의 치지 않는 쿼리다.

## 1-2. 기각된 가설 두 개

내가 유력하다고 본 최적화 두 개를 구현해서 측정했고, **둘 다 기각됐다.**

### 기각 ① Incremental 축소

가설: 키스트로크 검색은 단조 축소적이다. `route`의 후보는 `rout`의 후보의 부분집합이므로 첫 글자만 전체 스캔하면 된다.

| 시퀀스 | 전체 재스캔 p95 | Incremental p95 | 후보 수 |
|---|---:|---:|---:|
| `t` | 7.1 ms | 7.2 ms | 226,180 |
| `test` | 9.6 ms | 9.4 ms | 208,135 |
| `testsr` | 12.9 ms | 11.7 ms | 190,636 |
| `config` | 5.5 ms | 3.9 ms | 17,321 |

**논리적으로는 맞지만 실효가 없다.** 후보 집합이 19만 개로 유지되기 때문에 "19만 개를 재검사"하는 비용이 "23만 개를 스캔"하는 비용과 거의 같다. 쿼리가 선택적일 때(`config`, 후보 1.7만)만 1.4배 이득이 있었다.

→ 구현할 가치는 있으나 **성능 대책으로는 못 쓴다.**

### 기각 ② 저비용 그리디 스코어링

가설: 후보가 매우 많을 때는 정밀 랭킹이 무의미하므로 DP를 생략해도 된다.

속도는 빨라졌지만 **품질이 붕괴했다.**

| query | DP 대비 top-10 일치율 |
|---|---:|
| `router` | **0/10** |
| `tsconfig` | 0/10 |
| `testsr` | 0/10 |
| `apiserver` | 7/10 |
| **전체** | **25%** |

실제 출력:

```
query = "router"   ← 그리디 스코어링
      144  rust/tests/ui/lint/outer-forbid.stderr        ← ???
      144  rust/tests/ui/lint/outer-forbid.rs
      142  TypeScript/tests/baselines/.../thisInOuterClassBody.js
```

`router.js`가 top-3에 없다. 원인은 그리디가 **최좌측** 부분수열을 잡기 때문이다. `outer-forbid`에서 r-o-u-t-e-r이 흩어져 매치되면서 점수를 얻고, 정작 `router.js`의 연속 매치 보너스와 경쟁하지 못한다.

→ **채택 불가.** 검색기가 핵심 KPI인 제품에서 이런 결과는 즉시 신뢰를 잃는다.

## 1-3. 실제로 효과가 있었던 것

### fzf식 tight span (전진 + 후진 패스)

DP 구간을 "첫 매치~마지막 매치"가 아니라, 후진 패스로 **가장 조인 구간**으로 줄인다. 품질 손실 없음.

| query | DP span 평균 |
|---|---|
| `router` | 57 → **37** 바이트 |
| `tsconfig` | 66 → **50** |
| `rout` | 45 → **25** |

### SIMD 부분수열 스캔 (`memchr`)

바이트 루프 대신 다음 쿼리 문자로 벡터 점프.

**두 최적화 합계 기여도 (232K, p95):**

| query | baseline | +tight span | +SIMD | 이득 |
|---|---:|---:|---:|---:|
| `rout` | 36.4 ms | 28.0 ms | 22.5 ms | 1.6x |
| `router` | 40.9 ms | 33.2 ms | 29.7 ms | 1.4x |
| `testsr` | 51.1 ms | 38.5 ms | 37.6 ms | 1.4x |
| `config` | 14.2 ms | 13.4 ms | 10.7 ms | 1.3x |

**1.2~1.6배에 그쳤다.** 이것이 H5의 확인이다 — 병목은 DP가 아니라 **23만 경로의 15MB를 바이트 단위로 훑는 것 자체**이고, 이미 스칼라 메모리 대역폭 한계에 근접해 있다. 알고리즘 최적화로는 배수 개선이 나오지 않는다.

### 진짜 레버: 검색 범위를 파일명으로 제한

경로 전체(평균 68바이트) 대신 파일명만(평균 **27.2바이트**) 매칭하면 데이터가 **2.5배** 줄어든다.

| query | 경로 전체 p95 | 파일명만 p95 | 이득 |
|---|---:|---:|---:|
| `router` | 36.2 ms | **9.9 ms** | 3.7x |
| `testsr` | 39.8 ms | 14.0 ms | 2.8x |
| `tsconfig` | 16.9 ms | 6.1 ms | 2.8x |
| `rout` | 24.3 ms | 9.9 ms | 2.5x |
| `config` | 11.4 ms | 6.1 ms | 1.9x |
| `r` | 6.8 ms | 7.5 ms | 0.9x |
| `test` | 15.8 ms | 17.4 ms | 0.9x |

> `r`, `test`가 오히려 느린 이유: 파일명 모드에서는 마스크 프리필터로 거를 게 줄고 거의 모든 항목이 후보가 되어 DP를 타기 때문이다. 흔한 짧은 쿼리에서는 데이터 축소 효과가 상쇄된다.

## 1-6. 실험 1 결론

| 항목 | 리뷰의 주장 | 실측 | 판정 |
|---|---|---|---|
| 100K 경로가 메모리 ~10MB | 10MB | 6.6MB | **맞음** |
| 선형 스캔이 "수 ms" | 수 ms | 18.8ms (경로), 7.4ms (파일명) | **틀림 → 조건부** |
| 인덱스보다 스캔이 낫다 | 그렇다 | 퍼지 매칭이 역인덱스로 불가하므로 유지 | **맞음** |
| 비트마스크 프리필터 | (암묵적 기대) | 흔한 쿼리에서 무력 | **틀림** |

### 설계 반영 사항

1. **검색 범위 기본값을 파일명으로 한다.** 쿼리에 `/`가 포함되거나 사용자가 명시적으로 켤 때만 경로 전체로 확장한다. 이것이 유일하게 배수 효과를 낸 레버다.
2. **성능 목표를 하드웨어 조건과 함께 명시한다.** "16ms"만 쓰면 검증 불가능한 목표가 된다.
   - 4코어 이상, 100K 파일, 파일명 모드에서 p95 < 16ms
   - 2코어 최저 사양에서는 50K까지 보장
3. **문서 05의 인덱스 7종 중 Filename/Path/Extension은 인덱스가 아니라 in-memory 스캔이다.** 리뷰 §6의 3층 구조를 유지하되 "1층은 파일명 스코프가 기본"을 추가한다.
4. **Incremental 축소는 성능 대책이 아니라 취소(cancellation) 대책으로 위치시킨다.** 후보 집합을 들고 있으면 이전 결과를 즉시 그릴 수 있어 체감 지연을 줄인다.
5. **저비용 스코어링 폴백은 넣지 않는다.** 품질 붕괴가 확인됐다.

# 실험 2 — Stable ID 복구율

## 검증 대상 가정

리뷰 §2에서 제안한 계단식 해석:

```
L1. 경로 그대로 존재         → HIT (비용 0)
L2. alias 테이블(git rename) → HIT
L3. basename 유일 매칭       → 후보 제시 (1클릭 확정)
L4. 전부 실패                → BROKEN 표시, 링크는 보존
```

## 방법

실제 저장소 4개를 **전체 히스토리**로 클론하고, 과거 시점의 파일 목록을 "그때 사용자가 링크를 걸었다"고 가정한 뒤 HEAD 시점에 계단식으로 해석했다.

| 저장소 | 커밋 수 | 현재 파일 수 |
|---|---:|---:|
| django/django | 34,874 | 7,084 |
| scikit-learn | 33,925 | 1,818 |
| pallets/flask | 5,555 | 236 |
| psf/requests | 6,490 | 130 |

alias는 `git log --all --diff-filter=R -M`으로 히스토리 전체의 rename 체인을 수집해 압축(`a→b→c` ⇒ `a→c`)했다.

## 1차 측정의 결함과 정정

처음 측정에서 L4(복구 불가)가 11.4%로 나왔는데, 그 안에 **실제로 삭제된 파일**이 섞여 있었다. 삭제된 파일을 가리키던 링크가 깨지는 것은 전략의 실패가 아니라 정상 동작(L4의 정의 그대로)이다.

분모를 정정해 두 지표를 분리했다.

- **지표 A** — 과거에 건 링크 중 지금도 유효한 비율 (사용자 체감)
- **지표 B** — 대상이 여전히 존재하는 링크만을 분모로 한 복구율 (**전략의 실제 성능**)

## 결과

**저장소별 (지표 B, 대상이 살아있는 링크 기준):**

| 저장소 | 25% 경과 | 50% 경과 | 75% 경과 |
|---|---:|---:|---:|
| django | 99.9% | 99.6% | 86.8% |
| scikit-learn | 98.5% | 78.8% | 61.6% |
| flask | 100.0% | 94.3% | 73.0% |
| requests | 96.7% | 50.6% | 97.3% |

*50% 경과 = 2013~2016년에 링크를 걸고 2026년 현재 해석하는 시나리오.*

**종합 (50% 경과, 4개 저장소 6,040개 대상):**

| 단계 | 건수 | 비율 |
|---|---:|---:|
| 실제 삭제됨 (BROKEN이 정상) | 1,079 | 17.9% of 전체 |
| **대상이 살아있는 링크** | **4,961** | — |
| L1 경로 유지 | 4,375 | **88.2%** |
| L2 git alias 복구 | 371 | **7.5%** |
| L3u basename 유일 | 14 | 0.3% |
| L3a basename 모호 | 16 | 0.3% |
| L4 단서 없음 | 185 | 3.7% |

```
지표 A (전체 유효율)  = 78.6%
지표 B (전략 복구율)  = 95.7%     ← Stable ID 전략의 실제 성능
L3 오답 제안          = 0건
```

## 실험 2 결론

### ① 계단식 해석은 유효하다 — 95.7%

10년치 히스토리를 건너뛰고도 **대상이 존재하는 링크의 95.7%가 자동 복구**된다. 리뷰 §2의 "모든 노드에 Stable ID가 필요한 게 아니다 / 논리 주소 + 지연 해석으로 충분하다"는 판단은 실측으로 지지된다.

**content hash나 inode 기반 ID를 도입할 이유가 없다.** 그 복잡도 없이 95.7%가 나온다.

### ② L3(basename 매칭)은 빼야 한다

기여도가 **0.3%**다. 그런데 이걸 구현하려면 모호 후보 목록 UI, 사용자 확정 흐름, 오답 처리가 전부 따라온다. **0.3%를 위한 UI 복잡도는 정당화되지 않는다.**

→ **계단을 `L1 → L2 → BROKEN` 3단으로 단순화한다.** 이건 내 리뷰 §2에 대한 정정이다.

### ③ git 통합은 Phase 6이 아니라 Phase 0이다

L2의 7.5%는 전부 git rename detection에서 나왔다. 그리고 이 7.5%가 없으면 복구율이 88.2%로 떨어진다 — **7.5%p 차이가 "링크가 대체로 살아있다"와 "가끔 깨진다"를 가른다.**

문서 10은 Git을 **Phase 6**(마지막)에 두었다. 실측 근거상 **Phase 0**으로 올려야 한다. 리뷰 §2에서 추정으로 언급했던 것이 수치로 확인됐다.

### ④ 저장소 규모가 작을수록 복구율이 불안정하다

requests(130 파일)는 50% 경과에서 50.6%까지 떨어졌다. 소규모 저장소는 대규모 구조 개편(`requests/` → `src/requests/` 이전, vendored 패키지 제거)의 영향을 통째로 받기 때문이다. django(7,084 파일)는 같은 조건에서 99.6%였다.

→ **BROKEN 링크의 일괄 재지정 UI가 필요하다.** 구조 개편은 한 번에 수십~수백 개 링크를 깨뜨리므로 하나씩 고치게 하면 안 된다. "`requests/` → `src/requests/` 로 이동한 것 같습니다. 47개 링크를 일괄 수정할까요?" 형태의 접두사 규칙 제안이 실제로 필요한 기능이다. 리뷰에 없던 항목이다.

# 측정의 한계 (반증 가능성 확보를 위해 명시)

1. **2코어 / Xeon 2.1GHz는 실사용 환경보다 약하다.** 절대값이 아니라 한계점 위치와 상대 기여도로 읽어야 한다. 코어 스케일링 효율 0.86을 함께 측정해 외삽 근거를 남겼다.
2. **코퍼스가 극단 케이스다.** 232K는 대형 저장소 5개를 합친 규모다. 실제 vault 하나는 1K~50K가 일반적이며, 그 구간은 전부 여유 있게 통과한다.
3. **파일 레벨만 측정했다.** 리뷰 §2의 주소는 `path#symbol`인데 심볼 레벨 복구율은 재지 않았다. 함수명 변경 시 복구율은 별도 측정이 필요하다. 파일 레벨 95.7%는 **상한**으로 읽어야 한다.
4. **L2와 정답 판정에 모두 git을 썼다.** git이 추적하지 못한 이동은 L4나 DELETED로 분류되므로 순환 논증의 여지가 있다. 다만 이는 복구율을 **과대평가가 아니라 과소평가**하는 방향이므로 결론을 약화시키지 않는다.
5. **파이썬/장고 생태계에 치우쳤다.** Go/Rust/JS 저장소의 rename 패턴은 다를 수 있다.
