# 실험 3 — 심볼 레벨 Stable ID 복구율

## 측정한 계단

리뷰 §2의 주소는 `vault://path#Qualified.Name` 이다. 파일이 안 움직여도 함수가 개명되거나 다른 파일로 옮겨가면 링크가 깨진다.

```
S1. 같은 경로에 같은 qualname                  → HIT (비용 0)
S2. git alias로 옮긴 경로에 같은 qualname       → HIT
S3. vault 전체에서 qualname 유일                → 1클릭 확정
S4. 본문 유사도 매칭 (Jaccard ≥ 0.60)           → 1클릭 확정
S5. 실패
GONE. 오라클(Jaccard ≥ 0.30)도 못 찾음          → 심볼이 실제로 사라짐, 분모 제외
```

S4가 핵심 질문이었다. git이 파일 rename을 유사도로 잡아주듯 **심볼도 유사도 매칭이 필요한가?**

> 1차 구현에서 유사도 후보 검색이 `list(frozenset)[:80]`에 의존해 비결정적이었다. minhash 스케치로 교체해 재현성을 확보한 뒤 재측정했다. 아래는 정정판 결과다.


## 파일 레벨과의 비교 — 이것이 핵심

| | 파일 레벨 (실험 2) | 심볼 레벨 (실험 3) |
|---|---:|---:|
| 자동 복구 (L1+L2 / S1+S2) | **95.7%** | **80.0%** |
| L3 / S3+S4 추가 기여 | +0.2%p | **+13.7%p** |
| 최종 복구율 | 95.9% | 93.7% |
| 실제 소멸 비율 | 17.9% | 22.6% |

### ① 1차 보고서의 "상한" 경고는 맞았다

파일 레벨 95.7%를 심볼 주소에 그대로 적용하면 안 된다. 자동 복구는 **80.0%** 이고, 격차는 **15.7%p** 다. `path#symbol` 주소를 쓰는 이상 다섯 개 중 하나는 자동으로 안 풀린다.

### ② 내 §2 정정이 절반만 맞았다

실험 2 결과로 나는 이렇게 썼다.

> **L3(basename 매칭)은 빼야 한다. 기여도가 0.3%다.**
> **계단을 `L1 → L2 → BROKEN` 3단으로 단순화한다.**

**파일 레벨에서는 맞고, 심볼 레벨에서는 틀렸다.** 심볼 레벨에서 S3u(9.1%) + S4(4.5%)는 **13.7%p** 를 복구한다. 이걸 빼면 복구율이 93.7% → 80.0%로 떨어진다.

→ **계단을 레벨별로 다르게 설계해야 한다.**

```
파일 주소   vault://path
    L1 경로 존재 → L2 git alias → BROKEN
    (basename 휴리스틱 없음. 0.2%를 위해 모호 UI를 만들 이유가 없다)

심볼 주소   vault://path#Qualified.Name
    S1 동일 경로·동일 qualname
 →  S2 git alias 경로
 →  S3 qualname 전역 유일          (+9.1%p)
 →  S4 본문 유사도 Jaccard ≥ 0.60  (+4.5%p)
 →  BROKEN
```

이건 리뷰 §2와 1차 보고서 양쪽에 대한 정정이다.

### ③ 심볼 레벨에는 git의 `-M`에 해당하는 것이 없다 — 직접 만들어야 한다

S4로 복구된 945건 중 **74%(700건)가 이름이 유지된 채 파일만 이동**한 경우였다. 즉 `qualname`이 모호하거나(같은 이름이 여러 곳) 부모 클래스가 바뀌어 qualname이 달라진 케이스다.

git은 파일 단위로만 유사도 추적을 한다. **심볼 단위 유사도 추적은 이 제품이 직접 구현해야 하는 부분**이고, 4.5%p의 가치가 있다.

구현 비용은 낮다. 이 실험에서 쓴 것 전부:
- 토큰 4-gram의 crc32 집합
- minhash 스케치 96개
- 역인덱스 → 상위 40 후보 → 정확 Jaccard

파서가 이미 심볼 본문 범위를 알고 있으므로(문서 06의 Parser Adapter 출력에 `Source Ranges`가 있다) 추가 파싱 없이 인덱싱 시점에 계산할 수 있다.

### ④ 대규모 저장소일수록 안정적이다

같은 50% 경과에서 django(20,508 심볼) 93.8% vs requests(671 심볼) 89.5%. 특히 requests는 S1이 **1건**이었다 — 2013년의 모든 파일이 `requests/` → `src/requests/` 로 이동했기 때문이다. S2(git alias)가 205건을 건져내 89.5%를 만들었다.

→ 1차 보고서 §2-④에서 제안한 **BROKEN 일괄 재지정 UI**의 근거가 심볼 레벨에서도 재확인됐다. 그리고 이 케이스에서 알 수 있듯 **접두사 규칙 제안보다 git alias가 먼저 작동해야** 사용자가 아무것도 안 해도 된다.

# 실험 4 — 파서 선택 (리뷰 §7 재검증)

## 1차 측정: 내 주장이 지지되지 않았다

리뷰 §7에서 나는 tree-sitter를 권하며 이렇게 썼다.

> **문법 오류 항목이 결정적이다.** CPython `ast`는 그 순간 심볼을 **전부** 잃는다.

실험 3에서 부수적으로 측정한 결과는 이랬다.

| 대상 | .py 파일 | ast 성공 | ast SyntaxError | tree-sitter 무오류 |
|---|---:|---:|---:|---:|
| 과거 리비전 (2013~2016) | 2,482 | 99.8% | **0.2%** | 100.0% |
| HEAD (2026) | 3,993 | 99.8% | 0.2% | 99.97% |

**0.2%다.** 2014년 django 코드조차 Python 3.11 `ast`가 99.8% 파싱했다. "과거 코드라서 ast가 실패한다"는 논거는 **틀렸다.**

## 그런데 이 측정은 §7이 걱정한 상황이 아니었다

커밋된 코드는 정의상 문법이 유효하다. §7의 실제 논지는 이것이었다.

> "사용자는 편집 중인 파일을 저장한다. 편집 중인 파일은 절반은 문법 오류 상태다."

그래서 그 상황을 직접 재현했다. 실제 저장소 HEAD의 `.py` **322개**(원본 심볼 5,826개)에 실제 타이핑 중 상태를 주입했다.

| 편집 상태 | ast 파싱 성공 | ast 심볼 보존 | tree-sitter 심볼 보존 | 격차 |
|---|---:|---:|---:|---:|
| T1 파일 끝에서 함수 타이핑 중 (`def process_`) | 0.0% | **0.0%** | **99.9%** | 99.9%p |
| T2 괄호 미종료 (`def handle(request, context`) | 0.0% | **0.0%** | **99.9%** | 99.9%p |
| T3 문자열 미종료 | 0.0% | **0.0%** | **99.9%** | 99.9%p |
| T4 블록 헤더만 (`if settings.DEBUG:`) | 0.0% | **0.0%** | **99.9%** | 99.9%p |
| T5 중간 줄 삭제 (잘라내기 직후) | 73.6% | 68.7% | 92.4% | 23.7%p |
| T6 들여쓰기 붕괴 (블록 이동 중) | 41.0% | 31.4% | 89.7% | 58.3%p |
| **전체 평균** | **19.1%** | **16.7%** | **96.9%** | **80.3%p** |

*'심볼 보존' = 원본 파일의 심볼 중 그 상태에서도 찾아낸 비율. ast는 파싱에 실패하면 부분 결과 없이 0개가 된다.*

## 결론: 주장은 맞고 근거는 틀렸다

**T1~T4는 전부 0.0% 대 99.9%다.** 그리고 T1~T4는 예외적 상황이 아니라 **새 함수를 쓸 때 반드시 지나가는 상태**다. `def process_` 를 타이핑하는 매 순간 ast 기반 인덱서는 그 파일의 심볼을 전부 잃는다. Related 패널과 Graph가 타이핑 중에 비었다 채워졌다 한다.

- 리뷰 §7이 든 근거("과거 문법") → **기각.** 0.2%에 불과
- 리뷰 §7의 결론(Tree-sitter 채택) → **훨씬 강하게 지지.** 다만 이유는 "편집 중 상태"

문서 12는 이렇게 적혀 있다.

> Python AST는 native AST 가능, 다중 언어 확대 시 Tree-sitter가 유리

이 문장은 실시간 인덱싱이라는 사용 맥락을 빠뜨렸다. **저장 시점 배치 처리라면 ast로 충분하지만, 이 제품은 문서 09에서 "저장 즉시 Related 갱신"을 약속한다.** 그 맥락에서는 ast가 성립하지 않는다.

→ **Tree-sitter 단일 채택을 확정.** 배포 편의(단일 바이너리, 인터프리터 임베드 불필요)는 부차적 이유이고, **1차 이유는 편집 중 심볼 보존 80.3%p** 다.

# 측정의 한계

1. **Python 생태계만 측정했다.** Go/Rust/TS의 심볼 개명·이동 패턴은 다를 수 있다. 특히 Go는 파일 이동이 드물어 S1 비율이 더 높을 가능성이 있다.
2. **GONE 판정이 유사도 오라클(Jaccard ≥ 0.30)에 의존한다.** 함수를 완전히 재작성했지만 개념적으로 같은 함수인 경우 GONE으로 분류돼 분모에서 빠진다. 이는 복구율을 **과대평가**하는 방향이다. 반대로 S4 임계값(0.60)이 보수적이라 과소평가 요인도 있다.
3. **편집 상태 주입은 합성이다.** T1~T4는 실제 타이핑 순서를 재현했지만 실제 에디터 로그가 아니다. 다만 T1~T4의 결과가 0.0% 대 99.9%로 극단적이라 임계값 선택에 민감하지 않다.
4. **S4 유사도 파라미터를 튜닝하지 않았다.** 4-gram/스케치 96/임계 0.60은 첫 시도값이다. 튜닝하면 4.5%p가 더 올라갈 여지가 있다.
5. **가장 흔한 케이스인 "함수 본문만 수정"은 S1으로 잡힌다.** 이 실험은 개명·이동만 다루므로 일상적 편집의 복구율은 사실상 100%다.
