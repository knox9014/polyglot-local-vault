# 14. Locked Decisions

확정된 의사결정 목록이다. v0.2에서 **측정 근거가 있는 항목에는 근거를 명시**한다. 근거 없는 결정과 있는 결정을 구분하기 위해서다.

수치의 조건과 출처는 `17_MEASUREMENT_BASIS.md` 참조.

## 제품 범위

- 초기 버전은 컴퓨터 로컬 전용이다.
- 웹/모바일/클라우드부터 시작하지 않는다.
- P1(검색) 종료 시점에 **단독으로 쓸 만한** 도구가 되도록 자른다. 단 첫 출시는 P1이 아니다 — **MVP = P0~P3**이며 P1은 중간 점검 지점이다(→ `10_MVP_ROADMAP.md` "MVP 정의"). 조기 출시가 필요해지면 P1이 그 선택지로 남는다.

## AI

- AI는 핵심 정리 엔진이 아니다.
- AI 없이 Core가 완전히 작동해야 한다. **콜드스타트 해소도 AI 없이 한다.**
- AI는 MCP로 외부에서 연결한다.
- AI가 Graph를 자동으로 수정하지 않는다.
- AI 제안과 결정론적 제안은 같은 승인 파이프라인을 쓴다.

## 저장소 구조

- 원본 파일은 그대로 유지한다. 자체 포맷으로 강제 변환하지 않는다.
- **저장소를 2계층으로 분리한다.**

| | `.vault/` | `.vault-ai/` |
|---|---|---|
| 성격 | source of truth | 순수 파생물 |
| git | 커밋 대상 | ignore 대상 |
| 내용 | manual link, alias, 승인 이력, 설정 | 인덱스, 파서 캐시, 유사도 스케치, 미승인 제안 |

> **근거**: v0.1은 모든 시스템 데이터를 `.vault-ai/` 에 두면서 동시에 "삭제해도 재스캔으로 복구 가능"이라고 규정했다. manual link는 재스캔으로 복구할 수 없는 유일한 데이터이므로 자체 모순이었다.

- `links.jsonl` 은 append-only다. 삭제도 tombstone으로 기록한다 → Undo가 따라온다.

## Parsing

- **Tree-sitter 단일 백엔드.**

> **근거**: 편집 중 파일에서 심볼 보존율 96.9% vs CPython `ast` 16.7%. 특히 파일 끝에서 함수를 타이핑하는 중(`def process_`)에는 0.0% vs 99.9%. 이는 새 함수를 쓸 때 반드시 지나가는 상태다.
> 커밋된 코드에서는 `ast` 실패율이 0.2%에 불과했다 — "과거 문법 때문"이라는 이유는 사실이 아니다. 문제는 오직 편집 중 상태다.

- 부분 파싱 결과를 인덱스에 반영한다. 파싱 실패를 이유로 기존 심볼을 지우지 않는다.
- Parser Adapter 출력에 **shingle 스케치**와 **partial flag**를 포함한다.

## Graph

- 사용자의 명시적 링크가 중심이다.
- Parser가 확정할 수 있는 구조 관계는 자동 생성한다.
- **관계를 `origin`과 `confidence` 두 축으로 구분한다.**

```text
origin      manual / parser / git / suggested / imported
confidence  certain / probable / heuristic
```

> **근거**: v0.1은 `origin=parser` 하나로 `defined_in`(100% 확실)과 `calls`(오탐 다수)를 같이 취급했다. 신뢰 수준 판단이 성립하지 않았다.

- **`obj.foo()` 형태의 call edge를 생성하지 않는다.**

> **근거**: 호출부 360,893건 분석. vault 내 유일 해석률이 `foo()` 73.0%, `self.foo()` 75.3%, `obj.foo()` **30.3%**. 마지막은 오탐이 정탐의 2.3배다.

- 기본 UI는 `certain` 만, 1-hop 중심으로 보여준다.
- 거미줄형 Semantic Web을 사용한다.

## 링크 주소와 복구

- 논리 주소(`vault://path#Symbol`)를 저장하고 **조회 시점에 계단식으로 해석**한다.
- content hash / inode 기반 Stable ID를 도입하지 않는다.

> **근거**: 논리 주소 계단만으로 파일 95.7%, 심볼 93.7%를 달성했다. 추가 복잡도가 정당화되지 않는다.

- **계단의 깊이는 주소 종류마다 다르다.**

```text
파일   F1 경로 → F2 git alias → BROKEN                      (3단)
심볼   S1 → S2 → S3 이름 유일 → S4 본문 유사도 → BROKEN      (5단)
```

> **근거**: 파일 주소에서 이름 매칭의 기여도는 0.3%였으나, 심볼 주소에서는 S3+S4가 **13.7%p**를 채운다. 파일에서 뺀 단계를 심볼에서는 반드시 넣는다.

- 유사도 파라미터: **shingle k=3, sketch=32, threshold=0.40**

> **근거**: 45조합 스윕. 정밀도가 파라미터에 거의 무관(91.6~93.6%)하므로 임계값을 낮추는 것이 순이득이다. 0.60 → 0.40으로 복구 +87%, 정밀도 +0.6%p. 스케치 96 → 32는 결과 동일에 인덱스 -38%.

- BROKEN 링크를 삭제하지 않는다. 일괄 재지정 UI를 제공한다.

## Git

- **Git reader는 Phase 0 구성요소다.**

> **근거**: git rename 체인이 파일 링크 복구의 7.5%p, 심볼 링크 복구의 9.6%p를 담당한다. 대규모 구조 개편 시에는 사실상 전부를 담당한다 — 전체 파일이 이동한 5개 사례에서 git alias만으로 64~98%가 복구되었다.

- Git 히스토리 전체를 Graph에 넣지 않는다. rename 체인, 최근 커밋, 동시 변경만 반영한다.

## Search

- 파일 검색기는 핵심 제품 기능이며 속도가 최우선 KPI 중 하나다.
- **3층 구조**: in-memory path table / 역인덱스 / 임베디드 관계 저장소
- **기본 스코프는 파일명.** `/` 포함 시 경로 전체로 확장.

> **근거**: 100K 파일에서 경로 전체 18.8ms(예산 초과) vs 파일명 7.4ms. 경로 평균 68바이트 vs 파일명 27.2바이트.

- 파일명 검색에 역인덱스를 쓰지 않는다.

> **근거**: `tscfgjson` → `tsconfig.json` 같은 부분 문자 매칭은 term 단위 역인덱스로 표현할 수 없다.

- 저비용 스코어링 폴백을 두지 않는다.

> **근거**: DP 대비 top-10 일치율 25%. `router` 검색에 `outer-forbid.stderr` 가 1위로 나온다.

- Incremental 후보 축소는 성능 대책이 아니라 취소·체감 지연 대책이다.
- 초기 전체 인덱싱 후 incremental update를 사용한다.
- Exact / BM25 / Symbol / Graph 검색을 Core로 한다.
- Vector/Embedding은 Core가 아니다.
- **구문(phrase) 검색을 v0.1에 넣지 않는다.**

> **근거**: 위치 인덱스가 인덱스 크기를 원본 대비 5.5% → 21.8%로 확대한다.

## Watcher

- Watcher 이벤트는 저지연 힌트로만 쓰고 **주기 정합성 스캔으로 정확성을 보장**한다.
- 정합성 스캔은 **단일 스레드**로 구현한다.

> **근거**: 100K 파일 스캔 281ms + diff 60ms. 병렬화 시 오히려 2.3배 느렸다(I/O 바운드).

## Suggestion Engine

- **결정론적 규칙으로 관계 후보를 생성한다.** AI를 쓰지 않으므로 "AI 자동 수정 금지" 원칙과 충돌하지 않는다.
- 승인이 필요한 후보(R1·R3·R4)는 `.vault-ai/suggestions/` 에 저장되며 승인 후 `.vault/links.jsonl` 로 이동한다. R2·R6 는 문서에 명시적으로 쓰인 참조를 추출하는 것이므로 승인 없이 반영한다. MCP 경유 AI 제안은 재생성 불가라 `.vault/pending.jsonl` 로 간다.
- **필터링하지 않고 랭킹한다.**

> **근거**: 자동 정밀도 판정을 지역성과 산문 빈도 두 방식으로 시도했고 둘 다 실패했다. 지역성은 `docs/`와 `src/`가 분리된 표준 레이아웃에서 0.0%가 나왔고(정답이 교차 관계), 산문 빈도는 `ModelAdmin`(250회)과 `LoadBalancerSourceRanges`(8회) 같은 정답을 제거했다(좋은 문서는 API 이름을 산문에서도 반복한다).

- 영어 사전 필터를 쓰되 한계를 인정한다(`Ridge`, `Lasso` 같은 실존 심볼이 걸린다).
- **vendored 경로 제외는 Phase 0 필수**다. 성능이 아니라 정밀도 문제다.

> **근거**: node 기준 vendor 포함 764건 → 제외 155건. 제외된 609건은 대부분 무관한 외부 코드였다.

## 초기 파일 형식

```text
문서   .md  .rst  .txt
코드   .py  .go  .ts  .rs
데이터 .json  .yaml  .toml  .csv
노트북 .ipynb
```

> **근거**: `.rst`/`.txt` 추가 이유 — django는 문서를 `.txt`, cpython과 scikit-learn은 `.rst` 로 쓴다. `.md` 만 지원하면 이들에서 문서↔코드 관계가 0건이 된다. `.toml` 추가 이유 — R2(설정 값 ↔ 실존 경로, → `16_SUGGESTION_ENGINE.md`)가 JSON/YAML/TOML을 대상으로 하며 `.vault/vault.toml` 자체도 TOML이다.
> `.go`/`.ts`/`.rs` 추가 이유 — 심볼 링크 복구율이 이미 검증되었다(자동 80.2~94.5%, → `17` 언어별 표).

## 상호운용

- MCP를 핵심 외부 인터페이스로 사용한다.
- **툴은 4개로 압축한다**: `search` / `read` / `neighbors` / `link`
- 모든 응답에 `vault://` 주소를 포함한다 (주소 왕복성).
- 제안에 불변 ID를 발급한다.
- 특정 AI 모델에 종속되지 않는다.

## 성능 목표 (검증 가능한 형태)

목표는 하드웨어 조건과 함께 명시한다.

| 지표 | 목표 | 조건 |
|---|---:|---|
| keystroke → 첫 결과 p95 | < 16 ms | 2코어, 100K 파일, 파일명 스코프 (→ `17`: 100K 7.4ms) |
| 심볼 검색 p95 | < 50 ms | 2코어, 100K 파일. 실측 근거 없음 — UX 목표, CI 게이트 아님 (→ `05_FAST_LOCAL_SEARCH.md` 각주) |
| cold 전체 인덱싱 | < 30 s | 2코어, 단일 스레드, 100K 파일 (→ `17`: 18.5s) |
| 인덱스 크기 / 원본 | < 10 % | 위치 정보 제외 (→ `17`: 5.5%) |
| 정합성 스캔 | < 500 ms | 2코어, 단일 스레드, 100K 파일 (→ `17`: 281ms) |
| 파일 링크 자동 복구율 (CI 게이트) | > 93 % | 대상 생존 링크 기준, 2코어, 고정 저장소 (→ `17`: 실측 95.7%, 여유 2.7%p) |
| 심볼 링크 자동 복구율 (CI 게이트) | > 78 % | 대상 생존 링크 기준, 2코어, 고정 저장소 (→ `17`: 실측 80.0%, 여유 2.0%p) |
| 파일 링크 복구율 (1클릭 포함, 제품 목표) | 95.9 % | 사람이 후보를 1클릭 확정해야 나오는 수치 — 무인 CI로 측정 불가 (→ `17`) |
| 심볼 링크 복구율 (1클릭 포함, 제품 목표) | 93.7 % | 사람이 후보를 1클릭 확정해야 나오는 수치 — 무인 CI로 측정 불가 (→ `17`) |
| 편집 중 심볼 보존율 | > 95 % | 문법 오류 주입, Tree-sitter (→ `17`: 실측 96.9%, 여유 1.9%p) |

최저 사양(2코어)에서는 파일명 스코프 100K, 경로 전체 스코프 50K까지 보장한다. CI 러너는 이 2코어 사양(GitHub Actions 표준 러너)을 그대로 쓴다. → `12_ENGINEERING_DECISIONS.md` "벤치마크 회귀 테스트"(게이트 값 산출 근거·고정 저장소 SHA 규칙).
