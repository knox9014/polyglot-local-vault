# 10. MVP Roadmap

## MVP 정의

**MVP = Phase 0 ~ Phase 3.** 첫 출시는 여기서 한다.

```text
P0  Foundations          저장소 · watcher · git rename · 주소 체계
P1  Fast Search          파일 검색 + 최소 UI
P2  Parsers + Symbols    Tree-sitter · 심볼 검색
P3  Workspace + Graph    링크 · 그래프 · 제안 엔진        ← MVP 경계
─────────────────────────────────────────────────────────
P4  MCP                  v0.1 완성 (첫 출시 이후)
P5  Git 확장             v0.1 이후
```

**왜 P3인가.** 이 제품이 검증해야 하는 가설은 "코드와 문서를 잇는 도구에 빈 자리가 있다" 하나다(→ `01_PRODUCT_VISION.md` "차별점"). 그 가설을 실제로 시험하는 기능은 제안 엔진의 R1이고, R1은 P3에 있다. P2에서 멈추면 파서와 심볼 인덱스를 다 만들고도 **제품 가설은 한 번도 시험하지 않은 상태**가 된다.

**왜 P4가 아닌가.** MCP는 이 가설의 검증에 필요하지 않다. 외부 AI가 Vault를 읽을 수 있는지는 Vault 안에 읽을 만한 구조가 쌓인 뒤에야 의미가 있고, 그 구조를 만드는 것이 P3다. MCP를 MVP에 넣으면 검증이 한 Phase 더 늦어진다. v0.1 범위에서 빼지는 않는다 — 첫 출시 뒤 곧바로 붙인다.

**MVP를 무엇으로 판정하는가.**

```text
CI 게이트     P0~P3 의 각 Phase 종료 조건 (아래, 전부 결정론적)
실사용 게이트  Phase 3 승인율 — 첫 100건 중 30건 이상 승인 (사람이 판정)
```

승인율 게이트가 MVP 판정의 본체다. 나머지 종료 조건은 전부 "만들어졌는가"를 재고, 승인율만 "쓸모가 있는가"를 잰다. 이 값이 미달이면 Phase 4로 넘어가지 않는다 — 콜드스타트가 안 풀린 채로 MCP를 붙이면 빈 그래프를 노출하는 툴이 된다.

**MVP에서 하지 않는 것.** 아래 "v0.1에서 하지 않는 것"에 더해, P4(MCP)·P5(Git 확장)는 MVP 범위 밖이다.

### P1은 출시 지점이 아니라 중간 점검 지점이다

P1 종료 시점에 **빠른 로컬 파일 검색기 하나로는 이미 쓸 만하다.** 로드맵을 그렇게 잘라 둔 것은 맞다. 다만 그것을 첫 출시로 삼지 않는다 — fzf·Everything·Sourcegraph가 검색 축을 이미 점유하고 있어(→ `01_PRODUCT_VISION.md` "차별점") P1만 내놓으면 사용자는 얻지만 **제품 가설에 대해서는 아무것도 배우지 못한다.**

P1의 의미는 다른 데 있다: 이 시점부터 개발자 자신이 매일 쓸 수 있고, 이후 Phase는 실제로 쓰는 도구 위에 쌓인다. 사정이 바뀌어 조기 출시가 필요해지면 P1은 그 선택지로 남아 있다.

## Phase 재배열의 이유

v0.1 로드맵은 두 가지 문제가 있었다.

1. **Phase 3(Semantic Graph)이 Phase 4(Workspace)보다 앞이었다.** manual link를 구현해도 링크를 걸 UI가 없으면 아무도 링크를 걸 수 없다. Phase 3 종료 시점에 검증할 수 있는 것이 없다.
2. **Phase 6(Git)이 마지막이었다.** 측정 결과 git rename detection이 파일 링크 복구의 7.5%p, 심볼 링크 복구의 9.6%p를 담당한다. 대규모 구조 개편 시에는 사실상 전부를 담당한다(전체 파일 이동 5개 사례에서 git alias만으로 64~98% 복구). Phase 0으로 올려야 한다.
3. **종료 조건이 없었다.** "Phase 1 완료"를 무엇으로 판정하는지 정의되지 않았다.

또한 **P1 종료 시점에 이미 단독으로 쓸 만한 도구**가 되도록 잘랐다. v0.1 로드맵은 P4까지 가야 무언가 보였다.

## Phase 0 — Foundations

- Vault open / create
- `.vault/` 와 `.vault-ai/` 2계층 저장소
- ignore 규칙 (`.gitignore` 문법 재사용, vendored 기본 패턴)
- File watcher + **주기 정합성 스캔**
- **Git reader** — rename 체인 수집 → `aliases.jsonl`
- 논리 주소 체계 + 계단식 해석 골격
- Parser Adapter 인터페이스
- 인덱스 스키마 버전 / 다중 인스턴스 락
- ~~고정 저장소 13개의 SHA 를 `research/bench/PINNED_COMMITS.txt` 에 기록~~ — 완료 2026-08-17
- ~~고정 SHA 기준으로 링크 복구율 기준선 재측정~~ — 완료 2026-08-17. 자동 복구율 두 값이 그대로 재현돼 게이트를 조정하지 않았다 (→ `17` "확정 수치")
- ~~게이트를 돌릴 저장소 범위 확정~~ — 완료 2026-08-17. v0.1은 Python 4개, 게이트는 **합산 + 저장소별 하한 병행** (→ `12_ENGINEERING_DECISIONS.md` "게이트의 모집단")
- **파일 링크의 저장소별 하한 산출** — 실험 2를 저장소별로 집계하지 않았다. 심볼 쪽과 같은 방식으로 채운다

**종료 조건**

```text
정합성 스캔이 규모에 선형적으로 동작 (로컬, 소규모 코퍼스) ← Phase 0 판정용
git rename 체인이 aliases.jsonl 로 수집됨
.vault-ai/ 삭제 후 재인덱싱으로 완전 복구
고정 SHA 코퍼스에서 링크 복구율 기준선이 측정되고 `12` 의 게이트 값·대상 범위가 확정됨

정합성 스캔 < 500ms @ 100K 파일 (2코어)  ← CI 도입 후 확정. Phase 0 종료를 막지 않는다
  → `17`: 281ms (→ `12_ENGINEERING_DECISIONS.md` CI 게이트와 동일 값)
```

**성능 조건은 두 단계로 쪼갰다.** `< 500ms @ 100K (2코어)`는 개발 환경에서 판정할 수 없다 — 100K 코퍼스는 대형 저장소 5개를 합친 규모(→ `17` "검색 코퍼스")이고, 개발 머신은 CI 러너의 2코어 사양도 아니다. **측정할 수 없는 것을 Phase 종료 조건에 두면 Phase 가 끝나지 않는다**(B5·M6 에서 반복된 함정). 그래서 Phase 0 판정에는 "규모에 선형적으로 동작하는가"만 두고, 절대값 판정은 CI 가 붙는 시점으로 미룬다. **값과 조건은 그대로 살아 있다** — 미루는 것이지 낮추는 것이 아니다.

네 번째 조건은 Phase 0 에서 처음 생긴 것이다. `PINNED_COMMITS.txt` 의 SHA 는 `17` 의 원 수치를 만든 커밋이 아니어서(측정일 HEAD 가 기록돼 있지 않다) 재측정이 필요했다.

**2026-08-17 재측정에서 값 자체는 그대로 나왔다** — 파일 95.7% / 심볼 80.0%, 게이트 여유 2.7%p · 2.0%p 유지.

재측정 과정에서 **게이트의 모집단이 정의돼 있지 않았다는 것이 드러났다.** `> 78%`가 저장소 합산인지 저장소별인지가 미정이었고, 저장소별로 보면 최저 66.1%(scikit-learn)라 4개 중 2개가 게이트를 통과하지 못한다. **합산 > 78% + 저장소별 > 63% 병행**으로 정리했다(→ `12` "게이트의 모집단"). 파일 링크의 저장소별 하한은 아직 산출하지 않았다.

이전 버전은 "10K 파일 < 1s"였다. 실측이 100K에서 281ms라 10K 기준 1s는 약 35배 느슨해 아무것도 걸러내지 못했다. `12`가 이미 확정한 CI 게이트(100K, 2코어, < 500ms)를 그대로 가져온다.

## Phase 1 — Fast Search + 최소 UI

우선순위가 가장 높다.

- In-memory path table (1층)
- 파일명 스코프 기본 / `/` 포함 시 경로 확장
- 역인덱스 (2층) — 본문
- Incremental indexing
- 검색창 + 뷰어 (최소 UI)

**종료 조건**

```text
keystroke → 첫 결과 p95 < 16ms @ 100K 파일 (파일명 스코프, 2코어) → `17`: 7.4ms
cold 인덱싱 < 30s @ 100K 파일 (2코어, 단일 스레드) → `17`: 18.5s
인덱스 크기 / 원본 < 10% (위치 정보 제외) → `17`: 5.5%
```

세 항목 모두 하드웨어 조건(2코어, `17`의 측정 환경이자 CI 러너 사양)을 명시했다. 값 자체는 `12_ENGINEERING_DECISIONS.md`의 CI 게이트와 동일하다.

> 이 시점부터 빠른 로컬 파일 검색기로 매일 쓸 수 있다. 첫 출시로 삼지 않는 이유는 위 "P1은 출시 지점이 아니라 중간 점검 지점이다" 참조.

## Phase 2 — Parsers + Symbol Search

- Tree-sitter 백엔드
- `.md` `.rst` `.txt` `.py` `.go` `.ts` `.rs` `.json` `.yaml` `.toml` `.csv` `.ipynb`
- 심볼 인덱스 (2층)
- 심볼 본문 shingle 스케치 (S4용) → `.vault/sketches.jsonl` (→ `18_DATA_FORMATS.md` §4.4)
- 부분 파싱 결과 반영

**종료 조건**

```text
문법 오류 파일에서 심볼 보존율 > 95% (문법 오류 주입, Tree-sitter) → `17`: 96.9%, 여유 1.9%p
지원 형식 12종 전부에서 심볼이 추출되고 검색 결과가 vault:// 주소로 나온다
  (구조 검증 — 형식당 고정 샘플 1개, 결정론적)
```

**검색 성능이 아니라 검색 동작을 잰다.** 심볼 검색 p95는 아래 이유로 게이트에서 뺐는데, 그것만 빼면 Phase 이름이 "Symbol Search"인데 검색을 판정하는 조건이 하나도 남지 않는다. 그래서 성능 대신 **결정론적으로 검증 가능한 것** — 12종 형식 각각에서 심볼이 실제로 추출되고, 검색 결과가 다음 단계(링크 생성·MCP)가 쓸 수 있는 `vault://` 주소로 나오는지 — 를 조건으로 둔다. P4에서 "3회 호출 이내"를 구조 검증으로 바꾼 것과 같은 처리다.

**심볼 검색 p95 < 50ms 는 종료 조건에서 뺐다.** `17` 확정 수치 표에 없는 값이다 — 파일명 스코프 실측(7.4ms)에서 유추한 것이지 측정한 것이 아니다. 심볼 인덱스는 Phase 2에서 처음 만들어지므로 그 전에 잴 대상 자체가 없었다. M4(파일 저장 → 인덱스 반영 < 200ms)와 같은 처리로 **UX 목표로 남기고 CI 게이트에서 제외**한다(→ `05_FAST_LOCAL_SEARCH.md` "표준 사양 (4코어 이상)" 표 아래 각주). Phase 2에서 기준선을 측정한 뒤 게이트로 승격할지 판단한다.

M4를 "실측 근거 없는 유일한 성능 목표"라고 적었던 것은 틀렸다. 이 항목이 같은 상태로 `05`·`14`·`10` 세 곳에 실려 있었다. **"유일하다"는 판정도 전수 대조 없이 내리지 말 것** — B5의 "`05`에는 복구율 목표가 없다" 오판과 같은 계열이다.

## Phase 3 — Workspace + Graph + Suggestions

Graph와 UI와 제안 엔진을 **함께** 낸다. 셋 중 하나라도 빠지면 나머지의 가치가 검증되지 않는다. **MVP 경계이자 제품 가설의 검증 지점이다.**

- File tree / Editor / Related panel
- 링크 생성 UI
- Graph view (focus node 1-hop, confidence 필터)
- 계단식 해석 완성 (파일 3단 F1~F3 / 심볼 5단 S1~S5 / heading 3단 / JSON pointer 3단 / 열·행·셀 2단 → `18_DATA_FORMATS.md` §3)
- BROKEN 링크 표시 + 일괄 재지정
- **Suggestion Engine** — 규칙 R1~R6, 승인 정책은 규칙마다 다르다 (→ `16_SUGGESTION_ENGINE.md` "승인 정책")

```text
R6 Sphinx role · R2 설정값↔경로   승인 없이 자동 반영 → .vault-ai/
R1 · R3 · R4 · R5               승인 큐 → 검토 UI (초기 노출 상한 50건)
```

승인/거절 UI가 다루는 것은 **R1/R3/R4/R5 뿐이다.** R6/R2까지 큐에 넣으면 django 기준 7,867건이 한 화면에 쏟아져 B7이 그대로 재발한다(→ `09_DESKTOP_UX.md` "제안 검토 UI"). R5는 판정 성격상 R2(확인)에 가깝지만 생성량조차 미측정이라 자동 반영으로 올리지 않았다 — 근거는 → `16` "승인 정책".

**종료 조건**

```text
링크 생성 3클릭 이내
실제 프로젝트(flask, 236 파일) 첫 오픈 시
  검토 큐 후보 300건 이상 → `17`: 실측 585건, 여유 285건
심볼 링크 자동 복구율 > 78% (고정 저장소 회귀 테스트, 2코어 → `17`: 실측 80.0%, 여유 2.0%p)
파일 링크 자동 복구율 > 93% (고정 저장소 회귀 테스트, 2코어 → `17`: 실측 95.7%, 여유 2.7%p)
```

**모집단은 "검토 큐"다.** 자동 반영되는 R2·R6는 세지 않는다 — 이 게이트가 확인하려는 것은 사용자가 판정할 거리가 충분히 만들어지는가이고, 자동 반영분은 판정 대상이 아니다. 아래 승인율 게이트와 같은 모집단을 쓴다. 두 게이트가 서로 다른 모집단을 재면 Phase 통과 판정이 애매해진다.

이전 버전은 "실제 프로젝트"가 어느 저장소인지 지정하지 않았다. flask를 고른 이유는 **제안 생성량이 측정된 저장소 8개 중 심볼 수가 가장 작기 때문이다**(1,082 — 다음이 node 2,511, → `17`). 가장 불리한 조건에서 임계값을 잡는다. 링크 복구 코퍼스에도 들어 있어 다른 게이트와 같은 저장소를 쓴다.

R1 단독 수치로 임계값을 잡으면 깨진다 — 문서가 적은 저장소는 R1이 12건에 그치기도 한다(TypeScript, → `16`). 그래서 검토 큐 전체로 잡았다.

**"고정 저장소 중 최소 규모"라고 쓰지 않는다.** 이전 판이 그렇게 적었으나 `17`의 코퍼스 표에는 커밋 수만 있고 파일 수 열이 없다 — 확인할 수 없는 주장이었다(커밋 수로는 cobra 1,106이 flask 5,555보다 작다). 236 파일은 `git ls-files @ d318b683`으로 직접 센 값이고, 저장소 선정 근거는 위의 심볼 수다. **참고치와 정본을 섞지 않는다**(M1에서 정한 것).

**근거 수치를 `438`에서 `585`로 고쳤다.** 438은 세대가 다른 두 측정을 섞은 값이었다 — 그 R1 항은 `.md`만 훑던 초기 구현의 결과인 `0`이고, flask 문서는 `docs/*.rst`라 전량이 누락돼 있었다. 최종 규칙으로 다시 재니 R1은 156건이다(→ `17` "제안 후보 생성량 — flask 규칙별", `16` "생성량"). **다른 문서의 수치를 인용할 때 측정 세대를 확인할 것** — 규칙 구현이 바뀌면 같은 이름의 이전 수치는 폐기된 것이다.

1클릭 포함 링크 복구율(파일 95.9% / 심볼 93.6%, → `17`)은 제품 품질 목표이며 CI 종료 조건이 아니다 — 후보를 사람이 확정해야 나오는 수치라 무인 CI로 잴 수 없다. → `14_LOCKED_DECISIONS.md` "성능 목표".

**승인율 게이트 (실사용, CI 아님).** Phase 3 실사용에서 첫 100건의 제안 중 **30건 이상 승인**되어야 Phase 3를 종료된 것으로 본다. 이 값은 자동으로 측정할 수 없다 — 판정은 사람이 직접 한다. `17` "측정의 한계" §3이 밝히듯 자동 정밀도 지표 두 개가 실패했고 정밀도·승인율 모두 미측정이다. 따라서 여기서도 자동 정밀도 지표를 새로 만들지 않는다. **30건/100건(30%)은 실측 근거가 없는 초기값이다** — `16_SUGGESTION_ENGINE.md`가 초기 노출 상한 50건을 근거 없는 초기값으로 명시한 것과 같은 방식이다. Phase 3 실사용 데이터가 쌓이면 이 값을 조정한다. `01`이 R1을 "이 하나만 잘 돌아가도 제품이 성립한다"고 하는 핵심 주장에 대해, 후보의 **양**만 재던 이전 종료 조건에는 이 게이트가 없었다.

첫 100건은 검토 UI의 랭킹 상위 100건이다 — 무작위 표본이 아니다(→ `16` "후보 우선순위"). 랭킹이 제 역할을 하면 이 100건은 전체 후보 중 가장 승인될 만한 것들이고, **그럼에도 30%에 못 미치면 규칙 자체를 의심해야 한다**는 것이 이 게이트의 의도다.

**미달일 때는 랭킹부터 의심한다 — 규칙이 아니라.**

```text
1차   랭킹 신호와 가중치를 조정하고 다시 판정한다
      16 이 "가중치는 Phase 3 실사용 로그로 조정한다" 고 이미 적어 둔 그 작업이다
      규칙은 건드리지 않는다. 후보는 생성됐고 순서가 틀렸을 뿐일 수 있다

2차   재판정 후에도 미달이면 그때 규칙을 의심한다
      R1 의 이름 대조가 이 저장소에서 안 통하는지, 검토 큐 구성이 틀렸는지
```

랭킹을 먼저 보는 이유는 **생성량은 이미 확인됐기 때문이다**(flask 585건). 후보가 없어서 승인이 안 되는 것이 아니므로, 첫 100건에 좋은 후보가 안 실렸을 가능성을 먼저 배제한다. 가중치는 애초에 근거 없이 정한 값이라(→ `16` "후보 우선순위") 여기가 가장 먼저 흔들 자리다.

**2차까지 미달이면 제품 가설 자체를 재검토한다.** `01_PRODUCT_VISION.md`가 R1에 대해 "이 하나만 잘 돌아가도 제품이 성립한다"고 하는 주장이 실사용에서 반증된 것이므로, 로드맵을 이어가기 전에 그 판단을 먼저 내려야 한다. 이 경우를 문서에 적어두는 이유는, 게이트가 실패했을 때 조용히 임계값을 낮추는 것이 가장 흔한 대응이기 때문이다. **30%는 근거 없는 초기값이지만, 미달했다는 이유만으로 낮추지는 않는다.**

**초기 노출 상한 50건과 충돌하지 않는다.** 첫 화면은 상위 50건만 보여주지만 나머지는 사라지지 않고 페이징으로 남는다(→ `16` "초기 노출 상한"). 이 게이트는 사용자가 51번째 이후까지 판정을 이어간다는 것을 전제한다 — flask 검토 큐가 585건이므로 100건을 채울 후보 자체는 충분하다. **판정을 100건까지 이어가지 않는다는 것 자체가 신호다**: 상위 50건에서 승인할 것을 못 찾아 그만둔 것이므로, 그 경우도 게이트 미달로 본다.

## Phase 4 — MCP

MVP 범위 밖. **Phase 3 승인율 게이트를 통과한 뒤에 시작한다.**

- 4개 툴 (`search` / `read` / `neighbors` / `link`)
- 모든 응답에 `vault://` 주소 포함 (주소 왕복성)
- 제안 불변 ID + 승인 흐름

**종료 조건**

```text
모든 툴 응답에 vault:// 주소 + neighbors_hint 포함 (구조 검증 — 결정론적, 모델 불필요)
read-only 기본, write는 명시적 승인 후에만
```

이전 버전의 "3회 호출 이내로 해결"은 평균인지 전건인지, 대상 모델이 무엇인지 불명이었다. 확인해보니 애초에 종료 조건 자격이 없다 — `08_MCP_AND_AI.md` "미검증 항목"이 이미 "툴 개수와 스키마가 모델의 호출 효율에 미치는 영향은 실제 모델 하네스 없이는 잴 수 없다"고 밝히고 있다. 측정 불가능한 것을 종료 조건에 두면 Phase가 끝나지 않는다. 대신 결정론적으로 검증 가능한 것 — 모든 응답이 다음 호출을 만들 수 있는 `vault://` 주소와 `neighbors_hint`를 실제로 포함하는지 — 로 바꿨다. "X와 연결된 설정 찾아줘" 류 질의의 평균 호출 횟수(목표 3회 이내)는 `08_MCP_AND_AI.md`가 이미 적어 둔 대로 Phase 4 실사용 측정 항목으로 남긴다.

## Phase 5 — Git 확장

v0.1 이후. Phase 0에서 rename 체인만 읽었다면, 여기서 나머지를 붙인다.

- commit / diff / history / blame
- `changed_in` / `introduced_in` 관계
- 동시 변경 제안 (R4) 고도화

**종료 조건**

```text
commit / diff / history / blame 이 파일·심볼 주소로 조회됨
changed_in / introduced_in 이 links.jsonl 스키마로 표현됨 (→ `18_DATA_FORMATS.md` §5)
```

**성능 게이트를 두지 않았다.** git 이력 조회 성능은 측정한 적이 없고, 저장소 크기·이력 깊이에 따라 편차가 커서 100K 파일 같은 단일 조건으로 잴 수 없다. Phase 5 착수 시점에 측정 대상을 먼저 정한다. 여기서 수치를 지어내면 P0의 "10K < 1s"(35배 느슨했다)를 되풀이하는 것이다.

**1~7이 MVP다.** 8번만 첫 출시 이후다.

6번이 v0.2에서 추가되었다. 측정으로 달성 가능함이 확인된 항목이며(파일 95.7%, 심볼 93.6%), 이것이 없으면 나머지가 시간이 지나면서 무너진다.

7번이 MVP 안에 있는 것이 이 제품의 입장이다 — AI 없이 성립하지 않으면 MCP를 붙여도 성립하지 않는다(→ `01_PRODUCT_VISION.md` "핵심 가치").
