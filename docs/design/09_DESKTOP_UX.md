# 09. Desktop UX

## 기본 목표

내부 구조는 복잡하더라도 사용자는 처음에 복잡함을 느끼지 않아야 한다.

## 기본 레이아웃

```text
┌──────────────────────────────────────────────┐
│ Search                                       │
├────────────┬─────────────────────┬───────────┤
│            │                     │           │
│   Files    │       Editor        │ Related   │
│            │                     │           │
│ README.md  │                     │ Links     │
│ src/       │                     │ Graph     │
│ data/      │                     │ Backlinks │
│            │                     │           │
├────────────┴─────────────────────┴───────────┤
│ 관계 후보 N건  ·  BROKEN 링크 3건              │  ← 상태 표시줄
└──────────────────────────────────────────────┘
```

상태 표시줄이 v0.2에서 추가되었다. 제안 후보와 BROKEN 링크는 사용자가 찾아 들어가는 것이 아니라 **항상 보이되 방해하지 않아야** 한다.

N은 저장소마다 편차가 크고 수천 단위가 될 수 있다(실측 표 → `16_SUGGESTION_ENGINE.md`). 상태 표시줄은 미판정 총 건수를 그대로 보여준다 — "상위 50건" 같은 노출 상한 개념은 검토 화면에만 적용된다.


## Search UX

검색창에 입력하는 즉시 결과를 표시한다.

```text
r → ro → rou → rout → route → router
```

각 단계에서 파일명/심볼 결과를 즉시 갱신한다. 이것이 성립하려면 첫 결과가 한 프레임(16ms) 안에 나와야 한다. (→ `05_FAST_LOCAL_SEARCH.md`)

### 스코프 표시

기본 스코프는 파일명이다. 사용자가 이를 알 수 있어야 한다.

```text
router          [파일명]  ← 기본
src/router      [경로]    ← '/' 입력 시 자동 확장, 배지로 표시
```

배지를 클릭하면 스코프를 수동 전환할 수 있다.

경로 전체 스코프는 50K 파일까지만 16ms 프레임 예산 안에 든다. 그 이상(실측 100K = 18.8ms)은 예산 예외로 인정한다 — `/` 입력은 명시적 의도 표현이므로 소폭 지연을 받아들인다(→ `05_FAST_LOCAL_SEARCH.md`). 이 구간에서도 별도 UI는 없다: 아래 "단계별 결과 표시"와 같은 방식으로 새 결과가 도착할 때까지 이전 결과를 유지한다.

### 단계별 결과 표시

저비용 검색부터 즉시 그리고, 나머지는 비동기로 채운다. **결과가 갱신될 때 이미 그려진 항목이 튀지 않아야 한다** — 새 결과는 아래에 붙고, 순위 변동은 다음 키스트로크에서 반영한다.

```text
1. 파일명 / 경로 / 확장자   (첫 프레임)
2. 심볼                    (async)
3. 본문 exact / BM25       (async)
4. Graph 관련              (async)
```

## Related Panel

현재 객체의 관계를 보여준다.

```text
기본 표시   confidence = certain
            manual links / defined_in / contains / imports / json_pointer

필터로 표시  confidence = probable
            calls (bare, self) / inherits

표시 안 함   confidence = heuristic
            제안 검토 화면에서만
```

**편집 중에도 패널이 비지 않아야 한다.** 문법 오류 상태에서도 Tree-sitter가 부분 결과를 반환하므로, 파싱 실패를 이유로 기존 심볼을 지우지 않는다. (→ `06_POLYGLOT_PARSERS.md`)

## Graph UX

전체 Graph를 기본으로 보여주지 않는다. Focus Node 기반으로 관련 객체만 표시한다.

```text
기본     current node + 1-hop, certain 만
확장     1-hop → 2-hop → Project → Entire Vault
필터     confidence / relation type / layer
```

## 제안 검토 UI

콜드스타트를 해소하는 화면이다. (→ `16_SUGGESTION_ENGINE.md`)

**이 화면의 대상은 R1 / R3 / R4 뿐이다.** R6(Sphinx role)와 R2(설정값↔경로)는 경로·문법으로 확정되므로 승인 없이 자동 반영되어 큐에 들어오지 않는다(→ `16_SUGGESTION_ENGINE.md` "승인 정책"). 아래 목업·수치는 전부 R1 기준이다.

### 원칙 — 필터링이 아니라 랭킹

자동 정밀도 판정은 실패했다. 임계값으로 걸러내 "확실한 것만" 보여주려 하면 정답을 버린다. 대신 **전부 결정론적 신호로 랭킹해서, 상위 일부를 먼저 보여주고 사용자가 1클릭으로 판정**한다. 랭킹 신호와 초기 노출 상한은 → `16_SUGGESTION_ENGINE.md` "후보 우선순위".

실측 생성량은 저장소당 수백~수천 건이다(cpython 6,180건, django 4,721건 — → `16_SUGGESTION_ENGINE.md`의 실측 표). 128건이라는 작은 숫자로는 이 규모를 대표할 수 없으므로, 목업은 총 건수와 현재 노출 건수를 구분해 보여준다.

```text
┌─ 관계 후보 (상위 50건 표시 · 총 N건) ─────────┐
│                                              │
│ [문서 → 코드] 42건                            │
│   docs/ref/migration-operations.txt          │
│   `SeparateDatabaseAndState`                 │
│   → django/db/migrations/operations/special.py│
│                        [연결] [무시] [건너뛰기]│
│                                              │
│ [docstring → 심볼] 6건                        │
│ [함께 변경됨] 2건                             │
│                                              │
│              [더 보기]  [규칙별 전체 목록]      │
└──────────────────────────────────────────────┘
```

규칙별 줄의 숫자는 상위 50건이 규칙별로 어떻게 나뉘는지 보여주는 예시일 뿐, 실측치가 아니다.

- **연결** — `.vault/links.jsonl` 로 이동, `origin=manual`
- **무시** — `.vault/decisions.jsonl` 에 기록, 다시 제안하지 않음
- **건너뛰기** — 판정 보류, 다음에 다시 나옴

**상위 50건은 필터링이 아니라 랭킹 후 페이징이다.** 51번째 이후 후보도 `.vault-ai/suggestions/`에서 사라지지 않는다. **더 보기**로 다음 순위를 이어서 불러오거나, **규칙별 전체 목록**(문서→코드 / docstring→심볼 / 함께 변경됨)에서 원하는 규칙만 걸러 전체를 볼 수 있다.

### 중단 경계

한 번에 다 처리하지 않아도 된다. 판정하지 않은 후보(연결/무시하지 않고 화면을 닫거나 건너뛴 것)는 사라지지 않고 `.vault-ai/suggestions/`에 그대로 남으며, 다음에 이 화면을 열면 이어서 볼 수 있다. **건너뛰기**(위)는 개별 후보 단위의 판정 보류이고, 중단 경계는 화면 전체 단위 — 몇 건을 처리했든 나머지는 다음 세션까지 안전하게 유지된다는 보장이다.

### 일괄 처리

같은 규칙·같은 대상 파일의 후보를 묶어 한 번에 승인할 수 있다. 이 단위는 대상 파일 하나에 여러 R1 후보가 몰리는 경우(예: 한 README가 여러 심볼을 백틱으로 언급)에는 유효하지만, 후보가 수천 건 규모(→ `16_SUGGESTION_ENGINE.md`의 실측 표)로 대상 파일이 저마다 다르면 묶이는 폭이 좁다. 그런 경우 일괄 처리의 실효 범위는 랭킹 상위 50건 안에서 우연히 같은 파일로 묶이는 후보로 제한된다 — 전체 후보를 몇 번의 일괄 승인으로 끝낼 수 있다는 뜻은 아니다.

### 방해하지 않기

제안은 모달로 띄우지 않는다. 상태 표시줄에 건수만 표시하고, 사용자가 원할 때 연다. 첫 vault 오픈 시에만 한 번 안내한다.

## BROKEN 링크 UI

깨진 링크를 조용히 삭제하지 않는다. 사용자가 고칠 수 있는 정보를 시스템이 버려서는 안 된다.

### 개별 표시

Related 패널에서 BROKEN 링크는 회색 취소선으로 표시하고, 마지막으로 알려진 주소를 함께 보여준다.

### 일괄 재지정

대규모 구조 개편은 한 번에 수십~수백 개 링크를 깨뜨린다. 측정에서 `requests/` → `src/requests/` 이전 시 같은 경로에 남은 심볼이 **1건**까지 떨어진 사례가 있었다.

```text
┌─ 끊어진 링크 47건 ───────────────────────────┐
│                                              │
│ 공통 패턴이 감지되었습니다                     │
│   requests/  →  src/requests/                │
│                                              │
│ 47건을 일괄 수정할까요?     [수정] [개별 확인] │
└──────────────────────────────────────────────┘
```

접두사 규칙을 자동 도출해 제안한다. 개별 확인을 선택하면 하나씩 후보를 제시한다.

이 화면이 필요한 이유는 계단식 해석이 **자동으로 대부분을 처리하기 때문**이다. 자동 복구가 파일 95.7% / 심볼 80.0%이므로 사용자에게 남는 것은 소수의 잔여 케이스이고, 그 소수가 한 번에 몰려 온다.

## 인덱싱 진행 표시

cold 인덱싱은 100K 파일 기준 18.5초다. 그동안 앱이 멈춘 것처럼 보이면 안 된다.

```text
1층(파일명)이 먼저 완성되므로 검색은 즉시 가능하다.
2층(본문/심볼)은 백그라운드로 진행하며 진행률을 표시한다.
```
