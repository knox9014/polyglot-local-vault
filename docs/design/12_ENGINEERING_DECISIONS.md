## 미결 ② Search Ranking 가중치

초기 후보 순서:

```text
filename exact
> filename prefix
> symbol exact
> path match
> content exact
> BM25
> graph relation
```

퍼지 매칭 내부 가중치(경계 / camelCase / 연속 매치 / 파일명 영역 보너스)의 상대값도 미정이다. 현재 구현에서는 각각 8 / 7 / 8 / 4를 썼으나 근거는 없다.

**이것은 벤치마크로 정할 수 없다.** 정답이 사용자의 의도에 달려 있기 때문이다. 실사용 로그(무엇을 입력하고 몇 번째 결과를 선택했는가)로 조정해야 한다.

**결정 시점**: Phase 1 이후 실사용 데이터 축적 후.

## 벤치마크 회귀 테스트

확정된 항목은 되돌아가지 않도록 CI에 건다. **CI 러너는 GitHub Actions 표준 러너(2코어)**를 쓴다 — `17`의 측정 환경과 동일 사양이라 그대로 게이트로 쓸 수 있다. 러너 사양이 바뀌면 새 수치를 추정하지 않고 `17`을 다시 측정한 뒤 아래 게이트를 갱신한다.

```text
고정 코퍼스 (1K / 10K / 50K / 100K 파일, 2코어)
  keystroke p95 < 16ms (파일명 스코프, 2코어) → 17: 100K 7.4ms
  cold 인덱싱 < 30s @ 100K (2코어, 단일 스레드) → 17: 18.5s
  인덱스 크기 / 원본 < 10% (위치 정보 제외) → 17: 5.5%
  정합성 스캔 < 500ms @ 100K (2코어, 단일 스레드) → 17: 281ms

고정 저장소 (v0.1 은 python 4개, → 아래 "게이트의 모집단", "고정 저장소")
  자동 파일 링크 복구율   합산 > 93%   (대상 생존 링크 기준, 2코어)
  자동 심볼 링크 복구율   합산 > 78%   (대상 생존 링크 기준, 2코어)
                        저장소별 > 63% (최저 scikit-learn 66.1%, 여유 3.1%p)
  제안 후보 생성량        회귀 없음 (Phase 3에서 기준선 측정 후 고정)

문법 오류 주입
  심볼 보존율 > 95%
```

**게이트 값 근거** (→ `17` "확정 수치" · "링크 복구율")

- 자동 파일 링크 복구율 93%: 실측 95.7% − 여유 2.7%p
- 자동 심볼 링크 복구율 78%: 실측 80.0% − 여유 2.0%p
- 성능 게이트(keystroke / cold 인덱싱 / 정합성 스캔) 값은 `17`의 2코어 실측치에 이미 여유를 두고 있다. 값 자체는 변경하지 않았고, 조건(2코어)만 명시했다.

**1클릭 포함 복구율(심볼 93.6% / 파일 95.9%, → `17`)은 CI 게이트가 아니라 제품 품질 목표다.** 후보를 사람이 1클릭으로 확정해야 나오는 수치라 무인 CI로는 잴 수 없다. → `14_LOCKED_DECISIONS.md` "성능 목표".

**제안 후보 생성량 게이트에 적중률을 넣지 않는다.** 자동 정밀도 판정을 지역성·산문 빈도 두 방식으로 시도했고 둘 다 실패했다(→ `17` "측정으로 기각된 설계안", "측정의 한계" §3). 대신 고정 저장소에서 나오는 후보 수가 같은 입력에 같은 출력을 내는 성질(재현 가능)만 CI로 검증한다. 구체적 임계값은 `17`에 실측이 없으므로 Phase 3에서 기준선을 측정해 고정한다.

### 고정 저장소

`17`의 "링크 복구 코퍼스" 절에 실제로 적힌 13개 저장소(django, scikit-learn, flask, requests, hugo, cobra, gin, vue core, prettier, date-fns, tokio, clap, serde)를 그대로 쓴다. 저장소가 계속 갱신되므로 **각 저장소의 커밋 SHA를 고정**한다.

- SHA 목록은 `research/bench/PINNED_COMMITS.txt`에 저장소별 1줄(`<owner>/<repo> <sha>`)로 기록한다.
- **SHA는 2026-08-17에 채웠다** (`git ls-remote`로 각 기본 브랜치 HEAD를 받았다).
- CI 벤치마크는 **전체 히스토리를 클론한 뒤 이 SHA로 체크아웃**한다. 얕은 클론은 쓸 수 없다 — 링크 복구 측정이 git rename 체인을 따라가므로 히스토리가 없으면 측정 자체가 성립하지 않는다(→ `research/bench/README.md`).

```bash
git clone https://github.com/<owner>/<repo>.git
git -C <repo> checkout <sha>
```

**이전 판은 "얕은 체크아웃(shallow clone at SHA)"이라고 적었다.** 재현성만 보고 쓴 문장인데, 그렇게 하면 rename 체인이 없어 복구율 게이트(93% / 78%)를 측정할 수 없다. 재현성과 측정 가능성이 충돌하면 측정 가능성이 먼저다.

**고정된 SHA는 `17`의 원 수치를 만든 커밋이 아니었다 — 재측정으로 확인했다.** 원 측정(2026-08-16)은 HEAD를 기록해 두지 않았다. 2026-08-17에 위 SHA로 체크아웃해 실험 2·3을 다시 돌린 결과 **자동 복구율 두 값이 그대로 나왔고 게이트는 조정하지 않았다**(→ `17` "확정 수치"). 1클릭 포함 심볼 값만 93.7% → 93.6%로 내려갔으며 이는 CI 게이트가 아니다.

### 게이트의 모집단 — 합산 + 저장소별 하한

**`> 78%`가 무엇의 78%인지가 정의돼 있지 않았다.** 저장소를 전부 합쳐서 78%인지, 저장소마다 각각 78%를 넘어야 하는지에 따라 완전히 다른 시험이 된다. 측정해 보면 그 차이가 크다.

| 저장소 | 자동 (S1+S2) | +1클릭 |
|---|---:|---:|
| django | 82.4% | 93.8% |
| flask | 81.1% | 94.1% |
| requests | 67.5% | 89.5% |
| scikit-learn | **66.1%** | 92.9% |
| **합산** | **80.0%** | **93.6%** |

합산 80.0%는 심볼 수가 많은 django(16,935 / 20,837)에 끌려간 값이다. **저장소별로는 최저 66.1%로, 78% 게이트를 통과하는 저장소가 django·flask 둘뿐이다.** 저장소별 기준으로 CI를 짰다면 첫 실행부터 실패했을 것이다.

```text
합산 게이트      자동 심볼 > 78%   (실측 80.0%, 여유 2.0%p)
저장소별 하한    자동 심볼 > 63%   (실측 최저 66.1%, 여유 3.1%p)
```

**둘 다 건다.** 합산만 걸면 큰 저장소가 수치를 가려 작은 저장소의 회귀를 놓치고, 저장소별만 걸면 하한을 66% 아래로 내려야 해서 게이트가 헐거워진다. 병행하면 전체 품질(합산)과 개별 붕괴(하한)를 각각 잡는다. 두 값 모두 실측에 여유를 둔 것이며 추정치가 아니다.

파일 링크 게이트(93%)도 같은 구조가 필요하지만 **저장소별 하한은 아직 정하지 않았다** — 실험 2의 저장소별 자동 복구율을 따로 집계하지 않았다. Phase 0에서 같은 방식으로 채운다.

**미결 ③ — 게이트를 어느 저장소에서 돌릴 것인가.** 위 값의 출처는 고정 저장소 13개가 아니라 **그중 Python 4개**다. 나머지 9개(Go 3 / TypeScript 3 / Rust 3)는 M1(언어별 심볼 복구율)에서만 쓰였고 언어별로 80.2~94.5%로 퍼진다. 13개 전체에서 위 두 값이 성립하는지는 측정한 적이 없다.

**v0.1 CI는 Python 4개에서 돌린다.** Go/TypeScript/Rust 파서는 Phase 2에서야 생기므로 그 전에는 게이트를 걸 대상 코드가 없다. Phase 2에서 파서가 붙는 시점에 나머지 9개로 확장하고 두 값을 다시 유도한다. 근거 없이 범위를 먼저 넓히면 B5(도달 불가능한 게이트)가 재발한다.

측정 코드는 `vault-bench` 패키지에 있다. (→ `17_MEASUREMENT_BASIS.md`)
