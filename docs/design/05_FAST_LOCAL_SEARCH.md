# 05. Fast Local Search Engine

## 중요도

파일 검색기는 부가기능이 아니라 **Knowledge Graph와 동급의 핵심 제품 기능**이다.

목표:

> 사용자가 파일을 찾을 때 AI에게 물어볼 필요가 없을 정도로 기본 검색이 빨라야 한다.

이 문서의 수치는 전부 실측값이며 추정이 아니다. 측정 조건과 출처는 `17_MEASUREMENT_BASIS.md` 에 있다.

## 3층 구조

v0.1은 인덱스 7종(Filename / Path / Extension / Full-text / Symbol / Metadata / Graph)을 나열했다. 그대로 구현하면 5종을 각각 관리하며 원자적 갱신을 맞춰야 한다. 실제로 필요한 것은 3층이다.

```text
1층  In-memory path table
     대상: 파일명 / 경로 / 확장자 / 퍼지 매칭
     구조: flat byte buffer + 오프셋 테이블 (문자열 개별 할당 금지)
     방식: 인덱스 없이 전체 선형 스캔
     비용: 100K 파일 = 15MB 상주, p95 7.4ms

2층  역인덱스
     대상: 본문 / 심볼 / 메타데이터 (필드 분리)
     방식: 역인덱스 + BM25
     비용: 100K 파일 = 32MB, cold 구축 18.5s

3층  임베디드 관계 저장소
     대상: 노드 / 엣지 / alias / manual link
     방식: 재귀 순회 가능한 임베디드 DB
```

### 1층에 인덱스를 쓰지 않는 이유

파일명 퍼지 매칭은 **역인덱스로 표현할 수 없다.**

```text
쿼리 tscfgjson  →  TypeScript/src/tsconfig.json
쿼리 k8sapisrv  →  kubernetes/staging/src/k8s.io/apiserver/...
```

부분 문자 매칭이므로 term 단위 역인덱스로는 후보를 좁힐 수 없다. 10만 파일의 경로 문자열 전체가 6.6MB에 불과하므로 통째로 메모리에 올리고 선형 스캔하는 편이 빠르고 정확하다.

### 문자 집합 프리필터를 쓰지 않는 이유

64비트 문자 비트마스크로 후보를 거르는 방식을 측정했으나, 사용자가 실제로 입력하는 짧고 흔한 쿼리에서 통과율이 97%였다. 존재하지 않는 문자 조합에서만 작동한다. **비용 대비 효과가 없다.**

## 검색 범위 기본값

**기본 스코프는 파일명이다.** 쿼리에 `/` 가 포함되거나 사용자가 명시적으로 확장할 때만 경로 전체를 매칭한다.

이것이 성능에 가장 큰 영향을 준 단일 결정이다.

| 파일 수 | 경로 전체 p95 | 파일명 p95 |
|---:|---:|---:|
| 50,000 | 8.9 ms | 3.9 ms |
| 100,000 | **18.8 ms** (예산 초과) | **7.4 ms** |
| 232,126 | 34.6 ms | 17.7 ms |

경로 평균 68바이트 vs 파일명 평균 27.2바이트. 데이터가 2.5배 줄어든다.

## 검색 대상

- 파일명 (1층, 기본)
- 전체/상대 경로 (1층, 확장 시)
- 확장자 (1층)
- 파일 내용 (2층)
- 코드 심볼 (2층)
- 문서 heading (2층)
- JSON/YAML key (2층)
- Notebook cell (2층)
- 메타데이터 (2층)
- Graph 관계 (3층)

## 검색 문법

```text
router              파일명 퍼지 (기본)
src/router          '/' 포함 → 경로 전체로 확장
*.py                확장자
ext:json            확장자 명시
path:src            경로 한정
class:TeacherRouter 심볼 종류 한정
modified:7d         메타데이터
"exact phrase"      정확 문자열 (2층, 위치 정보 불필요한 방식)
```

## 매칭 알고리즘 (1층)

fzf 계열 구조를 따른다. 품질 손실 없이 비용을 줄이는 두 최적화를 포함한다.

```text
1. 전진 패스   SIMD 바이트 검색으로 다음 쿼리 문자로 점프
               (실패 시 즉시 탈락)
2. 후진 패스   끝 위치에서 거꾸로 매치해 가장 조인 구간을 찾는다
               → DP 구간이 경로 전체가 아니라 매치 영역으로 줄어든다
3. DP 스코어링 경계 / camelCase / 연속 매치 / 파일명 영역 보너스
4. top-K 선택  전체 정렬 대신 bounded 선택
```

DP 구간 축소 효과(측정): `router` 57 → 37 바이트, `rout` 45 → 25 바이트.

### 저비용 스코어링 폴백을 두지 않는다

후보가 많을 때 DP를 생략하고 그리디 스코어로 대체하는 방안을 측정했다. 속도는 빨라졌으나 DP 대비 top-10 일치율이 **25%** 였다.

```text
쿼리 "router" — 그리디 스코어링 결과
   1위  rust/tests/ui/lint/outer-forbid.stderr
   2위  rust/tests/ui/lint/outer-forbid.rs
```

`router.js` 가 top-3에 없다. 그리디가 최좌측 부분수열을 잡기 때문에 흩어진 매치가 연속 매치를 이긴다. **검색기가 핵심 KPI인 제품에서 채택할 수 없다.**

### Incremental 축소의 위치

키스트로크 검색은 단조 축소적이다(`route`의 후보 ⊆ `rout`의 후보). 그러나 성능 대책으로는 실효가 없다 — 후보 집합이 19만 개로 유지되면 재검사 비용이 전체 스캔과 같다. 측정상 선택적 쿼리에서만 1.4배 이득이 있었다.

**따라서 이것은 성능 대책이 아니라 취소(cancellation)·체감 지연 대책으로 위치시킨다.** 이전 후보 집합을 들고 있으면 새 결과가 나오기 전에 이전 결과를 즉시 다시 그릴 수 있다.

## 단계별 반환

체감 속도를 위해 저비용 검색부터 즉시 반환한다. 3층 구조와 대응된다.

```text
1. 1층 파일명/경로/확장자   → 첫 프레임에 그린다
2. 2층 심볼                 → async 갱신
3. 2층 본문 exact / BM25    → async 갱신
4. 3층 Graph 관련           → async 갱신
```

UI는 전체 검색이 끝날 때까지 기다리지 않는다.

## 인덱싱

### 초기

```text
Vault → 전체 스캔 → 파싱 → 인덱스 구축
```

### 이후

```text
파일 변경 → Watcher (저지연) ┐
주기 정합성 스캔 (보정)      ┴→ 변경 파일만 재파싱 → 관련 인덱스만 갱신
```

**부분 파싱 결과도 반영한다.** 편집 중 문법 오류가 있는 파일은 Tree-sitter가 부분 트리를 반환하므로, 살아남은 심볼로 인덱스를 갱신한다. 파싱 실패를 이유로 기존 심볼을 통째로 지우지 않는다. (→ `06_POLYGLOT_PARSERS.md`)

### 정합성 스캔

Watcher 이벤트는 유실된다. 주기 스캔이 안전망이다.

```text
비교 키   (path, mtime_ns, size)
주기      앱 시작 시 + 유휴 N분
비용      100K 파일 = 281ms 스캔 + 60ms diff
구현      단일 스레드 (I/O 바운드. 병렬화 시 오히려 2.3배 느림)
```

## 성능 목표

목표는 하드웨어 조건과 함께 명시한다. 조건 없는 "16ms"는 검증 불가능한 목표다.

기준 프레임 예산은 60fps 1프레임 = **16ms**다. 이 안에 첫 결과가 나오면 즉각적으로 느껴지고, 넘어가면 타이핑이 밀린다고 느껴진다.

### 표준 사양 (4코어 이상)

| 지표 | 목표 | 조건 |
|---|---:|---|
| keystroke → 첫 결과 p95 | < 16 ms | 100K 파일, 파일명 스코프 |
| 심볼 검색 p95 | < 50 ms | 100K 파일 |
| cold 전체 인덱싱 | < 30 s | 100K 파일 |
| 파일 저장 → 인덱스 반영 | < 200 ms | — |
| 정합성 스캔 | < 500 ms | 100K 파일 |
| 검색 취소 반응 | < 5 ms | — |
| 경로 테이블 상주 메모리 | < 20 MB | 100K 파일 |
| 전문 인덱스 크기 / 원본 | < 10 % | 위치 정보 제외 |

### 최저 사양 (2코어)

| 지표 | 보장 범위 |
|---|---|
| 파일명 스코프 p95 < 16ms | 100K 파일까지 (실측 7.4ms) |
| 경로 전체 스코프 p95 < 16ms | 50K 파일까지 (실측 8.9ms) |

병렬 효율 0.86이 실측되었으므로 코어 수에 따라 선형에 가깝게 개선된다.

### 인덱스 크기 목표의 근거

실측: 226,868 파일 / 1,329MB 원본 → 인덱스 72.8MB = **5.5%**. 단 이 인덱스는 doc ID만 저장한다.

| 구성 | 추가 | 누적 비율 |
|---|---|---:|
| doc ID only | — | 5.5% |
| + term frequency (BM25용) | +24MB | 7.3% |
| + 위치 정보 (구문 검색용) | +193MB | 21.8% |

**v0.1에서는 구문(phrase) 검색을 지원하지 않는다.** 위치 정보를 저장하지 않으면 목표가 7.3%로 여유롭다. 정확 문자열 검색은 후보 문서를 좁힌 뒤 원본을 직접 확인하는 방식으로 처리한다.

## Vector Search

Core에서 제외한다. Embedding은 모델 의존성을 만들고, 숫자·정확한 값 검색에 부적합하다.

```text
CORE
├─ Exact
├─ Prefix / Fuzzy
├─ BM25
├─ Symbol
└─ Graph

OPTIONAL PLUGIN
└─ Embedding / Vector Search
```

## 성능 원칙

- Incremental indexing
- flat buffer + 오프셋 (문자열 개별 할당 금지)
- SIMD 바이트 검색
- DP 구간 축소 (전진 + 후진 패스)
- 파일 변경 debounce 100~300ms
- 병렬 파싱 (CPU 바운드), 단일 스레드 메타데이터 스캔 (I/O 바운드)
- 1MB 초과 파일은 본문 인덱싱 제외, 5MB 초과는 파싱 제외
- 바이너리 제외 (첫 8KB 내 NUL 바이트 판정)
- ignore 규칙 (`.gitignore` 문법 재사용)
- 쿼리 cancellation
- 부분 결과 streaming

## 회귀 테스트

위 목표는 CI에 걸 수 있는 형태다. 벤치마크 코퍼스를 고정하고 다음을 회귀 검사한다.

```text
1K / 10K / 50K / 100K 파일 코퍼스
  → keystroke p95, cold indexing, 인덱스 크기, 정합성 스캔
심볼 링크 복구율
  → 고정 저장소 히스토리에서 93% 이상
편집 중 심볼 보존율
  → 문법 오류 주입 시 95% 이상
```
